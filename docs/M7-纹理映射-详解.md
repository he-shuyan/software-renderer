## 第一部分 · 全景

纹理映射要回答一个问题：**屏幕上一个像素，应该显示图片上的哪个颜色？**

完整链条有四个环节：

```
贴图（图片文件）        →  读进内存，成为像素数组
UV（每个顶点的坐标）    →  插值到面内每个像素
采样（UV → 像素）       →  在贴图上取一个颜色
着色（贴图色 × 亮度）   →  写进画布
```

M7 之前，三角形内部的颜色完全由三个顶点色插值而来；M7 之后，颜色来自一张图——**三角形的三个顶点变成了"贴图的三个定位点"**。

---

## 第二部分 · 贴图从哪来

我们用代码生成，而不是拿一张现成的图。原因有三：

1. **不依赖网络和素材版权**；
2. **可以精确控制图案**，便于验证；
3. **能设计"方向标记"**——棋盘格的亮度沿横纵方向有轻微变化，于是：

> 贴图一旦被翻转、镜像、旋转，方向标记会立刻显形。

如果贴一张纯色图或对称图案，UV 接反了你根本看不出来。**测试用的图案，要能暴露错误**——这和"验证数据要挑能手算的"是同一个思路。

## 第三部分 · BMP 读取

### 3.1 一个 24 位 BMP 的结构

```
偏移 0    2 字节   'B' 'M'
偏移 2    4 字节   文件总大小
偏移 10   4 字节   像素数据的起始偏移（通常 54）
偏移 18   4 字节   宽度
偏移 22   4 字节   高度
偏移 28   2 字节   每像素位数（24）
...
偏移 54   开始     像素数据：自下而上、BGR、每行补齐 4 字节
```

我们只取四个字段：**像素偏移、宽、高、位深**。其它字段（分辨率、调色板数量等）对这个格式的无压缩 24 位图没有影响。

### 3.2 读多字节整数：小端序

```cpp
static int readInt32(const unsigned char* p) {
    return p[0] | (p[1] << 8) | (p[2] << 16) | (p[3] << 24);
}
```

这就是 M1 那两个 `writeU32` / `writeU16` 的逆运算：

- 写：把整数按位拆开，低位先写；
- 读：把字节按位拼回来，低位先放。

`p[1] << 8` 是"把第二个字节挪到高 8 位"。四个字节拼完，就是一个 32 位整数 ✓

（注意 `unsigned char` 会自动提升为 `int`，所以移位不会溢出符号位 ✓ 宽度和高度也远不会到 2^31，不必担心符号问题 ✓）

### 3.3 `ifstream::read` 与 `reinterpret_cast`

```cpp
unsigned char header[54] = {};
in.read(reinterpret_cast<char*>(header), 54);
```

- `read(缓冲区, 字节数)` 一次读固定长度，**按二进制原样**读，不做任何文本转换 ✓
- 参数类型是 `char*`，而我们手里是 `unsigned char*`。两者在内存里完全一样，只是编译器要求显式转换 ✓ `reinterpret_cast` 的意思就是"按位重新解释这个指针" ✓
- `= {}` 把 54 个字节全部清零，即使文件比 54 字节短（读失败），后面也不会读到垃圾 ✓

### 3.4 `seekg`：跳着读

```cpp
in.seekg(dataOffset, std::ios::beg);   // 从文件开头跳到指定偏移
in.seekg(padding, std::ios::cur);      // 从当前位置再往后跳
```

**为什么不用"读满 54 字节就开始读像素"？** 因为文件头里写着像素数据从哪开始，而有些 BMP 在头和信息头之间还夹着调色板数据。**相信文件里写的偏移，而不是相信自己的假设** ✓

### 3.5 三条"反过来"

| 写的时候 | 读的时候 |
| --- | --- |
| 像素自下而上写 | 文件第 0 行 → 画布 `height − 1` 行 |
| 每像素写 B、G、R | 读进来按 B、G、R → 放回去要 R、G、B |
| 行尾补 0 到 4 的倍数 | 每行读完要跳过这些 0 |

**这三处只要错一个，图就会上下颠倒、颜色错乱或者整体斜掉。** 它们都是 M1 亲手写过的规则，M7 只是把它们倒过来执行一遍 ✓

### 3.6 往返测试

```
内存造图 → saveBMP → loadBMP → 逐像素比较
```

**为什么用 65×33 这个奇怪的尺寸？**

- `65 × 3 = 195`，不是 4 的倍数 → 每行补 1 个字节 → **padding 的代码真正被执行到** ✓
- 高度 33 是奇数 → 行序翻转如果写错，一定露馅 ✓

用 256×256 测，padding 恒为 0，那段代码等于没测过 ✓ **测试数据要能覆盖边界情形**，这是"设计测试"的核心功夫。

### 3.7 为什么后来改成"逐像素比较"而不是 `cmp`

`cmp` 比较的是**文件字节**。它要求两个文件的产生方式完全相同。

如果中途用画图打开看过、并且保存过，画图会用自己的结构重写 BMP（头部大小、尾部数据都可能不同），于是字节层面就不一样了——**哪怕每个像素都一致**。

所以我们测的是"**像素往返是否无损**"，这才是我们真正关心的性质 ✓

**通用经验**：测试要盯住"我要保证的性质"，而不是"顺手的那个动作"。字节相同只是像素相同的**充分条件**，不是必要条件 ✓

## 第四部分 · UV 与"顶点复用"的本质

### 4.1 现象：8 个位置，24 组 UV

立方体有 8 个角。但每个角出现在 3 个面上，而每个面都希望把贴图"正着铺满"，所以同一个角在不同面上要对应贴图的不同位置。

```
顶点 5（左下前角）：
  前面用 → (0, 0)
  左面用 → (1, 0)
  下面用 → (1, 1)
```

### 4.2 一个"顶点"到底是什么

在图形管线里，一个"顶点"不是"一个位置"，而是**一组属性的完整组合**：

```
顶点 = 位置 + UV + 法线（+ 颜色、切线……）
```

只要任意一个属性不同，就是**不同的顶点**——哪怕位置完全相同。

所以立方体的"带 UV 顶点"是 24 个（6 面 × 4 角），"带法线顶点"也是 24 个。真实模型文件里顶点数经常远大于几何顶点数，原因就在这里 ✓

### 4.3 这解释了 OBJ 的两个设计

- `v`（位置）、`vt`（UV）、`vn`（法线）**分别存三张表**；
- `f 5/1/2` 这种写法是"位置 5、UV 1、法线 2"的**自由组合**。

好处是：**同一个位置可以被不同面用不同的 UV 引用**，不必重复存坐标 ✓ 文件更小，而灵活性保留 ✓

## 第五部分 · UV 的本质与采样

### 5.1 UV 是什么

UV 是**贴图上的归一化坐标**：`(0,0)` 是一个角、`(1,1)` 是对角。它和像素尺寸无关——贴图是 256 还是 4096，UV 都是 0~1 ✓

### 5.2 三个必须做的处理

**第一，平铺。**

```cpp
const double tu = u - std::floor(u);
```

`1.3 → 0.3`、`−0.2 → 0.8` ✓ UV 超出 0~1 时自动回到开头，于是贴图会"重复平铺" ✓ 这是贴图平铺（tiling）的基础 ✓

**第二，v 轴翻转。**

```cpp
int y = static_cast<int>((1.0 - tv) * (tex.height() - 1));
```

OBJ 的 `v` 轴朝**上**（原点在左下）；`Image` 的 y 轴朝**下**（原点在左上）。不翻转，整张贴图上下颠倒 ✓

（这和 M6 那个"模型空间 y 向上、画布 y 向下"是同一类问题：**两个坐标系约定相反时，转换必须显式处理** ✓）

**第三，钳制。**

```cpp
x = std::max(0, std::min(tex.width() - 1, x));
```

理论上算出来的值一定在范围内，但浮点边界（`0.9999999 × 255 = 254.9999…`，或者刚好到 255）可能算出越界值。越界读 `vector` 是未定义行为 ✓ 一句钳制就消掉这个隐患 ✓

### 5.3 最近点采样与走样

```cpp
int x = tu * (width - 1);
```

直接取"落在哪个像素上"，不插值——这叫**最近点采样**（nearest neighbor）。便宜、边缘硬朗。

**但它会走样。** 当一个面以很小的角度被观察时，屏幕上相邻两个像素对应的 UV 差距很大，采样点会"跳过"整格，形成**莫尔条纹**（你在顶面上看到的那片糊）✓

解决办法是 **mipmap**（预先缩小若干级贴图，远处用小的那级）+ **双线性过滤**（取周围 4 个像素加权）。那是"采样质量"的进阶话题 ✓

## 第六部分 · 在光栅化里插值

M3 的 `w0, w1, w2` 到这里已经是第四次派上用场：

| 里程碑 | 插值的东西 |
| --- | --- |
| M3 | 颜色 |
| M5 | 深度 |
| M7 | UV |
| M8（将） | 法线 |

**同一组权重，插值任何顶点属性。** 这就是重心坐标的威力 ✓

### 6.1 调制

```cpp
c = texel × shade / 255;
```

- `texel`：贴图上的颜色；
- `shade`：顶点色插值出的亮度（贴图模式下把顶点色设成"白色 × 亮度"）；
- 两者相乘：贴图提供颜色，亮度提供明暗 ✓

**这是真实材质系统的基本结构**：`texture × diffuseColor × lighting` ✓

## 第七部分 · 透视校正（M7 的核心）

### 7.1 现象

- 倾斜面上的棋盘格被"鼓"出去；
- 四边形面沿着对角线出现一条错位折痕。

### 7.2 原因

**屏幕空间不是世界空间的等比缩放。**

透视投影把远处的空间压缩了：同样一米，近处在屏幕上占很多像素、远处只占几个。

所以：

- UV 沿三角形表面是**线性**变化的（在世界空间里）；
- 投影到屏幕以后，UV 随屏幕坐标的变化**不再是线性**的；
- 而光栅化是"屏幕上均匀地按重心权重插值"——相当于假定它线性 ✗

**那为什么会有对角线折痕？** 因为一个四边形面被拆成两个三角形，每个三角形各自在自己的屏幕上做仿射映射。两个三角形的映射在那条共享对角线上对不上，就出现了折痕 ✓

### 7.3 正确的量

对平面上任意一点，设它在相机空间的 `w`（距离）为 w，则：

> **`1/w` 在屏幕空间里是线性变化的**；并且对任意顶点属性 A，**`A/w` 在屏幕空间也是线性的**。

（直观理解：投影把空间压缩的倍数正好是 `1/w`，所以 `1/w` 随屏幕坐标线性变化；A 在世界空间线性，除以线性的 w 之后仍在屏幕空间线性——这是射影几何的一个基本结论。）

于是做法是：

```
1) 用重心权重插值 A/w  ->  得到 (A/w)_屏幕
2) 用重心权重插值 1/w  ->  得到 (1/w)_屏幕
3) A = (A/w)_屏幕 / (1/w)_屏幕
```

代码：

```cpp
const double iw = w0 * v0.invW + w1 * v1.invW + w2 * v2.invW;

const double u = (w0 * v0.uv.x * v0.invW +
                  w1 * v1.uv.x * v1.invW +
                  w2 * v2.uv.x * v2.invW) / iw;
```

**当所有 `invW` 都等于 1 时**（正交投影、2D 绘制），`iw = 1`，公式退化成普通插值 ✓ 所以一套代码同时服务两种投影 ✓

### 7.4 为什么深度不用校正

M6 把深度存成 `−1/w`。**它本身就是"屏幕空间的线性量"**，所以直接插值就是对的 ✓

而 UV 一开始存的是原值 `u`、`v` ✗ 它们在屏幕上不线性 ✗，所以必须换算成 `u/w` 再插 ✓

> **M6 那个"用 −1/w 当深度"的决定，在 M7 显出了它的另一层意义。**

### 7.5 验证方式

把校正前后的图各存一张，逐字节比较：

- **完全相同** → 校正没生效（最可能是 `invW` 忘了填，公式退化成仿射）；
- **不同** → 校正生效 ✓ 再看视觉：格子笔直、折痕消失 ✓

## 第九部分 · 代码对照

### 9.1 `loadBMP` 的关键四段

```cpp
// ① 验证身份
if (header[0] != 'B' || header[1] != 'M') return false;

// ② 只接受 24 位
if (width <= 0 || height <= 0 || bitCount != 24) return false;

// ③ 相信文件头里的偏移
in.seekg(dataOffset, std::ios::beg);

// ④ 行序翻转 + BGR->RGB + 跳 padding
const int y = height - 1 - fileRow;
out.setPixel(x, y, bgr[2], bgr[1], bgr[0]);
in.seekg(padding, std::ios::cur);
```

### 9.2 `sampleTexture` 的三步

```cpp
const double tu = u - std::floor(u);                  // 平铺
int x = static_cast<int>(tu * (tex.width() - 1));    // 映射
int y = static_cast<int>((1.0 - tv) * (tex.height() - 1));  // 翻转 v
x = std::max(0, std::min(tex.width() - 1, x));       // 钳制
```

### 9.3 光栅化里写颜色的顺序

```
判定内外 → 插值深度 → 深度测试 → 插值 UV → 采样 → 调制 → 写像素
```

**采样必须放在深度测试之后** ✓ 否则被遮挡的像素也会白白采样（浪费）✓ 而且深度测试的位置一旦写错，遮挡就全乱了 ✓

## 第十二部分 · 自测题

1. 24 位 BMP 的像素数据是按什么顺序存的？读的时候要怎么做？
2. `readInt32` 里为什么要 `p[1] << 8`？
3. 为什么读像素前要用 `seekg(dataOffset)`，而不是直接读第 54 字节？
4. 往返测试为什么用 65×33 而不是 256×256？
5. `cmp` 报"文件不同"，但像素可能完全一样——为什么？
6. 为什么立方体 8 个位置需要 24 组 UV？
7. 一个"顶点"在图形管线里包含哪些东西？
8. UV 的 `v` 为什么要翻转？
9. 透视投影下，屏幕空间里线性的是什么量？为什么 UV 不是？
10. 透视校正的公式是什么？`invW` 全为 1 时会怎样？
11. 为什么深度不需要透视校正？
12. 最近点采样为什么会走样？怎么缓解？
13. 贴图模式下为什么把顶点色设成"白色 × 亮度"？
14. 采样应该放在深度测试之前还是之后？为什么？

### 参考答案

1. 自下而上、每像素 BGR、每行补齐到 4 字节的倍数。读取时要：把文件第 0 行放到画布最后一行、把 BGR 换回 RGB、每行跳过填充。
2. 因为小端序：低字节在前。`p[1]` 是第二个字节，它代表数值的第 8~15 位，所以要左移 8 位。
3. 因为文件头里记录了像素数据的真实偏移，有些 BMP 中间还夹着调色板数据；相信文件里的字段，而不是假设固定是 54。
4. 65×3=195 不是 4 的倍数，能真正触发 padding 的读写；高度 33 是奇数，能暴露行序错误。256×256 时 padding 恒为 0，那段代码等于没测。
5. 因为 `cmp` 比的是文件字节。中途用画图保存过，画图会用自己的结构重写文件（头部/尾部可能不同），但像素内容可以完全一致。
6. 因为同一个位置在不同面上需要对应贴图的不同位置；位置相同但 UV 不同，就是不同的顶点。6 面 × 4 角 = 24。
7. 位置、UV、法线（以及颜色、切线等）的完整组合。任一项不同就是不同顶点。
8. OBJ 的 v 轴朝上（原点左下），而图像数组的 y 轴朝下（原点左上），方向相反必须显式翻转。
9. 线性的是 `1/w`，以及任意属性除以 w 后的 `A/w`。UV 本身在世界空间线性，但投影后随屏幕坐标不再线性。
10. `A = Σ(weight·A_i/w_i) / Σ(weight·w_i)`。`invW` 全为 1 时分母为 1，公式退化为普通线性插值（正交与 2D 都适用）。
11. 因为 M6 特意把深度存成 `−1/w`，它本身就是屏幕空间的线性量，直接插值即正确。
12. 掠射角下屏幕上相邻像素对应的 UV 跨度很大，采样会跳过整格，形成莫尔条纹。缓解：mipmap + 双线性过滤。
13. 调制是"贴图色 × 顶点色"。顶点色若带底色会给贴图染色；用白色 × 亮度，结果就是"贴图原色 × 亮度"。
14. 之后。先做深度测试，被遮挡的像素直接丢弃，可以省掉采样和调制的开销；顺序写反还会导致遮挡关系错误。

## 第十三部分 · 扩展练习

1. **双线性采样**：取 UV 周围 4 个像素做加权平均，观察顶面的莫尔条纹是否减轻。
2. **mipmap**：为贴图预生成 128、64、32… 几级缩小版，按屏幕上的 UV 变化率选择级别。
3. **UV 动画**：让 `u` 随时间偏移（`u + t`），贴图就会在表面流动。
4. **多张贴图**：给立方体的六个面用不同图片（需要扩展 OBJ 的 `usemtl` 或自己加一个面到贴图的映射）。
5. **用渐变贴图调试**：把贴图换成 `R = u×255, G = v×255`，透视校正是对是错，一眼就能看出来。
6. **对比三种插值**：普通线性、透视校正、以及"故意用 1/w 但不除回来"，观察三者差别。
