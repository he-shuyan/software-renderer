## 第一部分 · 问题的形式

M4 画线框时不需要考虑前后。一旦要填实心面，就必须回答：**立方体背面那三个三角形，凭什么被挡住？**

朴素想法是"后画的盖住先画的"（**画家算法**）。只要从远到近画就对。但它有两个死穴：

**死穴一：你得知道顺序。** 模型文件里的面是任意顺序的，要排序就得给每个面定一个"代表深度"，而一个面各处深度不同，取平均在多数情况凑合、少数情况出错。

**死穴二：有些情况根本排不出正确顺序。** 三个三角形可以互相穿插——A 的一部分在 B 前面、B 的一部分在 C 前面、C 的一部分又在 A 前面。无论怎么排序，总有一个面被错误遮挡。这是算法层面的限制，换更好的排序方法也解决不了。

## 第二部分 · Z-buffer 的思路转换

深度缓冲换了一条完全不同的路：**不排序，逐像素比深度。**

给每个像素配一个数字，记录"目前画到这里的最近深度"：

- 初始为"无穷远"；
- 每来一个三角形，逐像素算出该处的表面深度；
- **只有更近才覆盖颜色，并更新这个数字**；
- 否则丢弃。

**这是一次思路转换：把"全局可见性排序"这个难题，变成了"每个像素做一次局部比较"。** 顺序完全不重要。

代价是一张与画面同尺寸的深度图。2 MB（650×400）可接受；4K 就是 66 MB——显卡需要独立显存，一部分原因就在这里。

### 为什么是"越小越近"

模型空间的 z 轴朝向观察者（M4 的约定），所以 z 越大越靠前。取 `深度 = −z` 之后，**深度越小 = 越近**，与"存最小值"的直觉一致。

如果反过来（存 z、越大越近），代码也能跑，只是所有比较反号、初始化要用"负无穷"，读起来绕。**约定本身不重要，全项目一致才重要**——这正是 M2 那个"y 向下"的教训的延续。

### 为什么用严格小于

```cpp
if (depth < data[index]) { ... }     // 不是 <=
```

因为两个相邻三角形**共享一条边**，那条边上深度完全相等。用 `<=` 的话，后画的会覆盖先画的，结果就依赖绘制顺序——同一帧画面的细节会随三角形顺序抖动。用 `<` 让"相等则保持原样"，结果与顺序无关。

这也是图形学里"**z-fighting**"（深度冲突）问题的雏形：两个面深度极其接近时，谁赢取决于微不足道的浮点差别，画面会出现斑驳的条纹。真实引擎会用各种偏置技巧来缓解。

## 第三部分 · 深度插值

### 3.1 与颜色共用一组权重

```cpp
const double d = w0 * v0.depth + w1 * v1.depth + w2 * v2.depth;
```

这三个权重就是 M3 用来混合颜色的那三个数。**M3 说过"只要能在顶点上放数据，就能插到面内"，现在是第一次兑现**：位置插值出了像素的覆盖范围，颜色插值出了渐变，深度插值出了前后关系。M7 的纹理坐标、M8 的法线，都会走同一条路。

### 3.2 正交投影下为什么可以线性插值

正交投影下，屏幕上的均匀位移对应世界中的均匀位移，所以深度沿屏幕是线性的，重心坐标直接插值就是正确的。

**透视投影下不成立**：近处的三角形在屏幕上占的像素多，远处的占得少，深度在屏幕上呈 1/z 分布。那时正确的做法是插值 **1/z**，再取倒数。

M6 换成透视投影时会回来改这一行。这个细节很多人第一次写透视渲染时都会漏掉，症状是"纹理/深度在斜面上分布不均匀"。

## 第四部分 · 重构：`ScreenVertex` 与共用核心

### 4.1 为什么要把属性打包

M3 里积累过一个真实的坑：**交换顶点统一绕序时，忘了同时交换颜色**，结果形状对、渐变方向反了。

`ScreenVertex` 把位置、深度、颜色放进同一个结构体之后，`std::swap(v1, v2)` 一次就交换了全部属性，**这个坑从结构上消失了**。

这条经验可以推广：

> **反复一起传递、一起修改的数据，就应该打包在同一个类型里。** 否则"记得一起改"这件事迟早会忘。

它同时也是 GPU 里的概念：一个顶点带着它的所有属性（位置、法线、纹理坐标……）。

### 4.2 共用核心与两个薄入口

```cpp
static void rasterizeTriangle(Image& image, DepthBuffer* depth,
                              ScreenVertex v0, ScreenVertex v1, ScreenVertex v2);
```

一个实现，两个入口：

- `drawTriangle(image, p0..p2, c0..c2)` → 传 `nullptr`，不做深度测试；
- `drawTriangleDepth(image, depth, v0..v2)` → 传 `&depth`，做深度测试。

这样避免了"复制一份改一改"带来的双份维护（M2 就在这类重复代码上栽过一次）。

### 4.3 关于"可以指向空的参数"

`DepthBuffer*` 是指针，可以被赋成 `nullptr` 表示"没有这个东西"。所以它天然适合表达"可选参数"。循环里那句：

```cpp
if (depth != nullptr && !depth->testAndSet(x, y, d)) {
    continue;
}
```

就是"如果传了深度缓冲，就测试它"。

（指针的完整规则以后再专门讲。现在记住两点：`&变量` 取地址得到一个指针；`指针->成员` 等价于 `(*指针).成员`。）

## 第五部分 · 叉积与面法线

### 5.1 叉积的几何意义

```cpp
Vec3 cross(const Vec3& other) const {
    return Vec3(y * other.z - z * other.y,
                z * other.x - x * other.z,
                x * other.y - y * other.x);
}
```

- 结果**同时垂直于**两个输入；
- 方向由**右手定则**决定；
- 长度等于两者张成的**平行四边形面积**。

它**只在三维里有定义**。（二维里有一个退化的版本，只返回一个数，我们在 M3 的 `edge` 函数里用过。）

### 5.2 交换顺序，方向反转

```cpp
Vec3(1,0,0).cross(Vec3(0,1,0))  == (0, 0, 1)
Vec3(0,1,0).cross(Vec3(1,0,0))  == (0, 0, -1)
```

**这就是"绕序决定正面朝向"的数学根源。** M4 里在 `cube.obj` 中耐心按"从外面看逆时针"写的顶点顺序，M5 才开始真正发挥作用——面法线指向外，背面剔除才能正确工作。

### 5.3 用两个边向量确定平面朝向

```cpp
const Vec3 n = (b - a).cross(c - a).normalized();
```

`(b−a)` 与 `(c−a)` 是同一个面的两条边。用它们叉积就得到平面法线——这也解释了**为什么三个点足以确定一个平面**。

### 5.4 法线 → 颜色：调试视图

```cpp
Color normalColor(const Vec3& n) {
    return Color(255 * (0.5 + 0.5 * n.x), ...);
}
```

这正是 M3 那个 `hueColor` 的推广：把方向的分量线性映射到 RGB。

- M3：一个角度（2D 方向）→ 色相环；
- M5：一个三维方向 → RGB。

**这是图形学里最常用的可视化手法。** 以后调试法线、切线、光照方向、速度场，都用它：一张图就能看出方向对不对。

但要注意：**这种着色的目的是"可读"，不是"好看"**。三个面拿到的是坐标轴的映射色，彼此没有视觉关系；而且面内没有变化（平面着色），看起来像色块拼贴。

### 5.5 平面着色与平滑着色

| | 平面着色（flat） | 平滑着色（Gouraud / Phong） |
| --- | --- | --- |
| 每个像素的颜色 | 整个面一个颜色 | 由顶点法线插值而来 |
| 看圆球时 | 能数出一个个多边形 | 看起来是光滑的曲面 |
| 用在哪 | 立方体这类硬边物体 | 曲面物体 |

M5 用的是面法线（平面着色）。M8 会读取 OBJ 里的顶点法线做平滑着色，那时圆球才会"圆"起来。

## 第六部分 · 背面剔除

### 6.1 为什么可以剔除

法线的 z 分量为负，说明这个面背对观察者，**不可能被看见**——它确实会被深度测试丢掉，但那时已经白算了重心坐标、插值、比较。

```cpp
if (n.z <= 0.0) {
    continue;
}
```

正交投影下视线平行于 z 轴，观察者在 +z 侧，所以"朝向观察者"就是 `n.z > 0`。（透视投影下视线不再平行，需要用"面中心到相机"的方向做判断，M6 再说。）

### 6.2 代价与收益

代价：每个面一次点积（实际只看了 z 分量，更省）。
收益：立方体 12 个三角形丢掉 6 个，**填充像素量减半**。

这是性价比最高的一类优化：**几个时钟周期的判断，省掉一半的像素工作量。**

### 6.3 怎么验证它是对的

**优化不改变输出，只改变代价。** 所以验收方式是两条：

1. 数量对得上：`正面三角形 = 6，被剔除 = 6`；
2. **画面与剔除前逐像素相同**。

第 2 条是真正的考验。如果图变了，说明绕序判断反了——法线指向内侧，你把正面剔掉了。排查手法：把被剔除的面用另一种颜色也画出来，看哪些面被误判；或者干脆关掉剔除逐帧对比。

## 第七部分 · 优化方法论（这一段值得抄下来）

M5 里出现了一个真实的流程问题：**着色改动和剔除改动被放在同一次构建里**，于是"剔除前后画面完全一致"这条验收就没法做了——因为颜色本来就变了。

由此得出两条通用规则：

**规则一：一次只改一件事。** 尤其是性能优化。优化的工作量在于"确信自己没改变行为"，而"确信"来自"只有这一个变量"。

**规则二：优化必须有可比较的验收。** M5 用的是"输出逐像素不变 + 计数减半"。别的场景可以用：耗时（跑一百次取平均）、内存占用、文件大小。

如果没有这两条，"优化"很容易变成"改坏了但看不出来"。

## 第八部分 · 三种着色模式与"好看"这件事

| 模式 | 形式 | 设计意图 |
| --- | --- | --- |
| 0 | 深度冷暖渐变 | **表现**：近暖远冷是人眼判断远近的天然线索，看着像被打过柔光 |
| 1 | 法线映射成 RGB | **调试**：颜色之间没有视觉关系，但能一眼看出朝向 |
| 2 | 深度基调 × 法线明暗 | 两者相乘：颜色给基调，点积给明暗 |

**"新图没原来的好看"是个有价值的观察。** 它不是哪张图"更高级"，而是**两张图在回答不同的问题**：

- 深度渐变回答"这个物体有多厚、哪里近"；
- 法线颜色回答"每个面朝哪边"。

**模式 2 才是最能表达体积的那一个**，因为它的结构就是真实光照的骨架：

```
最终颜色 = 材质颜色 × (环境光 + 漫反射强度)
```

其中"漫反射强度"就是 `max(0, n·L)`——法线与光照方向的点积。M2 学的点积，到这里第一次变成了画面上的明暗。

## 第十部分 · 自测题

1. 画家算法为什么解决不了"三个三角形互相穿插"的情况？
2. Z-buffer 为什么不需要按深度排序？
3. 深度缓冲的内存代价怎么估算？650×400 大约多少？
4. 为什么深度测试用 `<` 而不是 `<=`？
5. 为什么我们把深度定义为 `−z` 而不是 `z`？
6. 正交投影下可以直接插值 z，透视投影下为什么不行？应该插值什么？
7. `ScreenVertex` 这样的"属性打包"解决了 M3 里的哪个具体问题？
8. `rasterizeTriangle` 的参数 `DepthBuffer* depth` 为 `nullptr` 时表示什么？
9. 为什么"交换叉积的两个向量"会得到方向相反的法线？这跟绕序有什么关系？
10. 背面剔除判断 `n.z <= 0` 的依据是什么？
11. 验证一个优化"没改变行为"，M5 用的是什么方法？
12. 模式 2 的公式 `颜色 × (0.35 + 0.65 × max(0, n·L))` 里，`n·L` 的物理含义是什么？

### 参考答案

1. 因为它需要先给出一个全局的深度顺序，而互相穿插的三角形不存在任何正确的全局顺序。
2. 因为它不排序——每个像素自己记住"目前最近的深度"，来的三角形更近就覆盖、更远就丢弃，顺序无关。
3. 像素数 × 每像素字节数。650×400 = 26 万像素 × 8 字节（double）≈ 2 MB。
4. 两个相邻三角形共享边，那条边上深度相等。用 `<=` 会让后画的覆盖先画的，结果依赖绘制顺序；用 `<` 则相等时保持不变。
5. 模型空间 z 朝向观察者，取负之后"越小越近"，与"存最小值"的直觉一致。约定本身不重要，全项目一致才重要。
6. 因为透视投影下屏幕上的均匀位移不对应世界中的均匀位移，深度呈 1/z 分布。透视投影下应插值 1/z，再取倒数。
7. 解决了"交换顶点统一绕序时忘了同时交换颜色"——打包后 `std::swap` 一次交换所有属性。
8. 表示"没有深度缓冲"，即不做深度测试（2D 绘制用这个入口）。
9. 叉积满足反对称性 `a × b = −(b × a)`。顶点顺序反过来，两条边向量的叉积就反向，法线随之反向——所以绕序决定了面的正面朝向。
10. 正交投影下视线平行于 z 轴、观察者在 +z 一侧，所以法线 z 分量为正即朝向观察者。
11. "输出逐像素不变" + "计数减半"（正面 6 / 剔除 6）。
12. 它是面法线与光照方向的点积，几何上等于两者夹角的余弦——夹角越小（面越正对光源），值越大，面越亮。这就是漫反射。

## 第十一部分 · 扩展练习

1. 把深度测试写成"输出深度图"的模式：用插值出的深度当灰度值画一张图，直观看看 Z-buffer 里存了什么。
2. 试着把光照方向改成随鼠标/参数可调，观察亮面怎么移动（这已经是简单的交互式着色了）。
3. 关掉背面剔除，用两种颜色分别画正面和背面，确认绕序判断是对的。
4. 给 `DepthBuffer` 加一个"深度冲突"实验：故意让两个面深度相差 1e-12，观察斑驳条纹（z-fighting）。
5. 在 M4 的立方体旁边再放一个立方体（用模型矩阵平移），验证两个物体之间的遮挡关系。
6. 用 `std::chrono` 测一下开/关背面剔除的渲染耗时，看看"填充量减半"在时间上体现多少。
