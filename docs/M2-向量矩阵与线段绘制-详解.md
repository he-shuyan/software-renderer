## 第一部分 · M2 全景

M1 造好了画布：一块能按 `(x, y)` 读写颜色的内存。M2 给这块画布装上"笔"和"手"：

- **笔**：给定两个端点，算出中间要点亮哪些格子。这是**光栅化**——项目名字"软光栅化渲染器"里的那个词，M2 才第一次真正做它。
- **手**：用矩阵把图形缩放、旋转、平移。这是**变换**。

两者合起来就是渲染管线的雏形：**顶点 → 矩阵变换 → 光栅化 → 像素**。

---

## 第二部分 · 屏幕坐标：一个必须先接受的约定

画布用屏幕坐标：**原点在左上角，x 向右，y 向下**。

这和数学课上"y 向上"正好相反。原因是历史的：早期显示器（CRT）的电子束从上往下一行行扫描，所以内存里第一行数据对应屏幕最上面一行。这个约定被所有图形 API 继承下来，改不动了。

三个后果，会在整个项目里反复出现：

1. **数学上的逆时针旋转，在屏幕上看起来是顺时针。** 因为整个坐标系被上下镜像了一次。
2. **画线时 y 越大越靠下。** 说"往下走"就是 y 增加。
3. **以后学 3D 投影时，要么翻转 y，要么在投影矩阵里塞一个负号。** 这是所有人都要过的一关。

## 第三部分 · `Vec2`：把向量变成一种类型

### 3.1 为什么不直接传两个 double

`drawLine(image, x0, y0, x1, y1, ...)` 也能工作，但一旦开始写 `lerp`、`transformPoint`、法线、纹理坐标，参数列表会失控，而且**每个函数都要自己重新推导同一套运算**。把向量做成类型，运算就只写一遍，出错机会只有一处。

### 3.2 `struct` 还是 `class`

两者在 C++ 里几乎一样，区别只在默认访问权限：`struct` 默认 public，`class` 默认 private。纯数据 + 小函数用 `struct` 是圈内惯例。

### 3.3 运算符重载：`a + b` 到底是什么

```cpp
Vec2 operator+(const Vec2& other) const {
    return Vec2(x + other.x, y + other.y);
}
```

C++ 允许把运算符当函数名用。写 `a + b` 时，编译器实际调用 `a.operator+(b)`。所以你能写出像数学公式一样的代码，而不是 `a.add(b)`。

### 3.4 为什么必须返回新对象，不能返回引用

如果返回 `Vec2&`，你返回的是函数里那个局部对象的引用。函数一返回，局部对象就被销毁了，引用指向的是已经失效的内存——这叫**悬垂引用**。用它不会立刻崩，而是随机出怪事。

**返回新对象（值语义）** 是 C++ 的默认安全选择：编译器会帮你拷贝/移动，成本也被优化得几乎为零。

### 3.5 尾部那个 `const`

```cpp
Vec2 operator+(const Vec2& other) const
                                  ^^^^^
```

它承诺"这个函数不修改对象自己"。两个好处：编译器帮你检查（真改了会报错），以及 `const Vec2` 对象也能调用它。凡是"读了数据、不改自己"的函数都该加。

### 3.6 点积的几何意义

```cpp
double dot(const Vec2& other) const {
    return x * other.x + y * other.y;
}
```

它的几何含义是 `|a| · |b| · cosθ`——衡量两个向量"有多同向"。同向为正、垂直为 0、反向为负。

现在它看起来只是个乘法加法，但 M8 的光照模型（Blinn-Phong）整个就是围绕点积转的：光线方向与法线的点积决定表面有多亮。

### 3.7 `length` 与 `normalized`

```cpp
double length() const {
    return std::sqrt(x * x + y * y);
}

Vec2 normalized() const {
    const double len = length();
    if (len == 0.0) {
        return Vec2(0.0, 0.0);
    }
    return Vec2(x / len, y / len);
}
```

`length` 就是勾股定理。`normalized` 把向量缩成长度 1，**只保留方向、丢掉距离**——以后表示"朝向"时全用它。

命名值得注意：是 `normalized()` 而不是 `normalize()`。**前者暗示"返回一个新向量"（所以能加尾部 const），后者暗示"修改我自己"。名称本身就是文档。**

那个 `if (len == 0.0)` 是除零保护：零向量没有方向，除以 0 会得到 NaN，而 NaN 会像病毒一样污染整个画面。（顺带：浮点数一般不该用 `==` 比较，但"是否恰好等于零"是少数安全场景。）

### 3.8 一条自检式的不变量

`a.normalized().length()` 必须等于 1。写完任何几何代码，先想一个"结果必须满足什么"的关系，这种习惯比记住具体数值有用得多。

## 第四部分 · `Color` 与线性插值

### 4.1 为什么颜色也要成为类型

三个 `uint8_t` 参数在函数签名里就是三个数，看不出哪个是红、哪个是蓝，参数一多必然写错顺序。变成类型之后，`Color(255, 80, 80)` 自带说明。

### 4.2 `lerp`：图形学里出现频率最高的函数

```cpp
inline Color lerp(const Color& a, const Color& b, double t) {
    const double r = a.r + (b.r - a.r) * t;
    ...
}
```

公式 `a + (b − a) · t`，含义是"从 a 出发，朝 b 走 t 这么远的比例"：

- `t = 0` → 结果就是 a
- `t = 1` → 结果就是 b
- `t = 0.5` → 正中间

它的用途远不止颜色：M5 用它插值深度值，M7 用它插值纹理坐标，M8 用它插值法线。**凡是"两个端点之间要平滑过渡"的地方，都是 lerp。**

### 4.3 打印 `uint8_t` 的陷阱

```cpp
std::cout << mid.r;                          // ✗ 打印出一个乱码字符
std::cout << static_cast<int>(mid.r);        // ✓ 打印数字
```

`std::uint8_t` 本质是 `unsigned char`，`cout` 会把它当成**字符**输出。要打印 8 位整数，一律先转 `int`。这个坑在打印像素值、文件头字节时都会再遇到。

### 4.4 头文件里的自由函数必须写 `inline`

```cpp
inline Color lerp(...)     // ← 这个 inline 不能省
```

头文件会被多个 .cpp 包含。**写在类外面的自由函数**如果不加 `inline`，两个 .cpp 各生成一份定义，链接时就报 `multiple definition of lerp`。**类内定义的成员函数**（比如 `Vec2::dot`）自动带内联语义，不用写。

一句话记住：**类内的成员函数不用管，写在头文件里的自由函数必须加 `inline`。**

## 第五部分 · DDA 画线

### 5.1 问题定义

屏幕是离散格子，直线是连续的。画线的本质是：**挑出最接近理想直线的那串格子**。这个动作叫光栅化。

### 5.2 `steps` 为什么取两个方向的最大值

```cpp
const int steps = static_cast<int>(std::fabs(dx) > std::fabs(dy) ? std::fabs(dx) : std::fabs(dy));
```

规则是"**沿较长的那条轴每次走一格**"。如果只按 `|dx|` 算步数，遇到陡线（`|dy|` 远大于 `|dx|`）时，每步 y 会往下跳十几格，画出来是一串断开的点——M2-2.3 你亲眼验证过这个现象。

### 5.3 为什么用 `lround` 而不是强转

`static_cast<int>(x)` 是**截断**（0.9 变 0），会让整条线往左上方偏半个像素。`std::lround(x)` 是**四舍五入**，线才会落在理想位置的正中间。

### 5.4 循环边界 `<= steps`

从 `i = 0` 数到 `i = steps`，一共 `steps + 1` 个点，正好包含起点和终点。写成 `< steps` 会丢掉最后一个像素——这类"差一个"的错误叫 off-by-one，是画线代码里最常见的 bug。

### 5.5 整数运算的"先乘后除"

```cpp
255 * x / (width - 1)      // ✓ 先乘后除
255 / (width - 1) * x      // ✗ 先除：255 / 649 = 0，结果全 0
```

C++ 里两个整数相除会直接截断。**只要看到"整数除整数"，就检查一下顺序。**

### 5.6 DDA 的两个固有弱点

1. **每步都有浮点运算**：一次加法加一次四舍五入，长线上就是几千次。
2. **误差会累积**：`xStep` 是无限小数，存进 double 那一刻就被截过一次，累加上千次后偏差可能被四舍五入放大成一个像素。

这正是 Bresenham 存在的理由。

## 第六部分 · Bresenham 画线

### 6.1 半像素判据（先只看缓斜线）

限制线是"向右、斜率 0~1"（`0 ≤ dy ≤ dx`）。此时 x 每一列都会经过，问题只剩一个：**y 要不要抬一格？**

理想直线在列 x 的高度是 `y0 + (x − x0) · dy / dx`。维护一个浮点误差 `e`，表示"当前像素比理想线低了多少"：

```
每右移一列：e += dy / dx
如果 e ≥ 0.5：y 抬一格，e -= 1
```

**超过半格就抬** —— 这就是"四舍五入"的逐步版本。

### 6.2 整数化：两边同乘 `2dx`

| 原来的东西 | 乘 `2dx` 之后 |
| --- | --- |
| `e` 每步增加 `dy/dx` | `E` 每步增加 `2dy` |
| 判断 `e ≥ 0.5` | 判断 `E ≥ dx` |
| `e = e − 1` | `E = E − 2dx` |

于是浮点、除法、四舍五入全部消失，只剩整数加法和一次比较。

### 6.3 手算轨迹表（用 `(0,0) → (5,2)`）

正确的执行过程（`dx = 5`、`dy = 2`、`err = 3`）：

| i | 画在哪 | 进循环时 err | e2 = 2×err | 走 x | 走 y |
| --- | --- | --- | --- | --- | --- |
| 0 | (0, 0) | 3 | 6 | 是 | 否 |
| 1 | (1, 0) | 1 | 2 | 是 | 是 |
| 2 | (2, 1) | 4 | 8 | 是 | 否 |
| 3 | (3, 1) | 2 | 4 | 是 | 是 |
| 4 | (4, 2) | 5 | 10 | 是 | 否 |
| 5 | (5, 2) | — | — | 到达终点，结束 | |

规律是"**x 每一步都走，y 只在需要时跟一格**"。如果 x 和 y 交替前进，说明误差项或判断写错了。

（另外记住初值的重要性：`e` 的初值差半个像素，整条线就会整体偏移。）

### 6.4 推广到八个方向

- **`sx` / `sy`**：每一步 x 和 y 该往哪边走（+1 或 −1），靠三目运算符算出。
- **`dx` / `dy` 取绝对值**：只要跨度，方向交给 `sx` / `sy`。
- **两个独立的 `if`**：`if (e2 > -dy)` 决定 x 走不走，`if (e2 < dx)` 决定 y 走不走。

**绝对不能写成 `if / else if`。** 45° 附近两条同时成立，一次要往两个方向各走一步（斜角步）。写成 `else if` 之后，斜角步永远不会发生，线会变成横竖交替的锯齿——这正是 M2 里实际踩到的坑。

### 6.5 常见错误

| 症状 | 原因 |
| --- | --- |
| 线短一格 | `break` 放在了画点之前 |
| 45° 附近缺格子 | 两个判断写成了 `if / else if` |
| 整体偏移半个像素 | `err` 初值写错 |
| 走成锯齿、目标不对 | 终点坐标写错（比如 `y1` 用了 `to.x`） |
| 编译报 `assignment of read-only variable 'x0'` | 给会被 `+=` 修改的变量加了 `const` |

最后一条提醒：**加 `const` 的时候在脑子里过一遍"它在这个函数里会被改吗"**——`x0`、`y0` 会动，`x1`、`y1`、`dx`、`dy`、`sx`、`sy` 不会动。

## 第七部分 · 怎么验证几何代码

### 7.1 手算对照

挑一组能手算的输入（`(0,0) → (5,2)` 就是特意选的），让程序把**内部结果**打印出来，和纸上算的逐一比对。这比"看着图挺好"可靠一万倍。

### 7.2 差分测试与"允许的误差范围"

两个独立实现画同一条线，逐像素统计差异。这条测试线理论上有 `max(560, 285) + 1 = 561` 个点，实测两个都是 561，不一致 6 个。

**为什么允许差异？** 在"理想高度正好是半格"的位置上，DDA 的 `lround` 会向上取整，而 Bresenham 的比较符号可能选择不抬——一个像素的分歧，各贡献 2 个差异像素。这条线上有 5 处这样的位置，其中 3 处产生了分歧，3 × 2 = 6 ✓

**关键在于：先算出理论值，再想清楚允许的误差范围，最后才看实测。** 只会看"通过/失败"的人做不了测试；能判断"这个偏差算不算正常"的人才能。

### 7.3 不变量测试

```cpp
transformPoint(rot * trans, p)  ==  transformPoint(rot, transformPoint(trans, p))
```

这条等式由矩阵乘法的定义保证，**和具体数值无关**。它的好处是不需要预先知道正确答案，只要看两边是否一致；而且换任何矩阵、任何维度都成立。

图形学里这类不变量很多：单位化后的向量长度必为 1、深度值随距离单调、颜色插值两端等于端点色。**能想到不变量，就能写出不怕改动的测试。**

### 7.4 为什么测试要拆成独立程序

- `app`：给别人看的东西，输出干净、跑得快。
- `tests`：给自己用的东西，只关心"每个模块还对不对"。

以后每加一个功能，就在 `tests.cpp` 里补一段验证，**跑一次就知道有没有把旧功能碰坏**。这叫回归测试——它是"能长期写下去的项目"和"写到一半烂掉的项目"之间的分界线。

## 第八部分 · 齐次坐标与 `Mat3`

### 8.1 为什么 2×2 做不到平移

2×2 矩阵作用在点上的形式是 `x' = ax + by`、`y' = cx + dy`。把原点 `(0,0)` 代进去，结果永远是 `(0,0)`——**2×2 变换必定把原点留在原地**，而平移的本质就是把原点挪走。所以这不是写法问题，是数学上做不到。

### 8.2 那个补上去的 1

给点补一个坐标变成 `(x, y, 1)`，用 3×3 矩阵：

```
[x']   [1  0  tx]   [x]
[y'] = [0  1  ty] · [y]
[w ]   [0  0  1 ]   [1]
```

第一行：`x' = 1·x + 0·y + tx·1 = x + tx` ✓ 平移就被"乘"出来了。**那个 1 的作用就是让 `tx` 那一列原封不动地加到结果上**；如果补 0，平移项就被乘没了。

### 8.3 `w` 与透视除法

第三行算出 `w`，最后结果要除以 `w`。现在 `w` 恒等于 1（因为矩阵第三行是 `0 0 1`），除 1 看不出效果——但它是 M6 的伏笔：3D 投影时 `w` 会等于"距离相机的远近"，除以 `w` 就是近大远小的来源。**现在把这个除法写进 `transformPoint`，M6 一行都不用改。**

由此也得到一条硬性要求：**仿射变换矩阵的 `m[2][2]` 必须是 1**。它一旦是 0，`w` 就是 0，整个变换失效——M2 里实际踩过这个坑，五个测试一起输出 `(0,0)`。

### 8.4 `m[3][3] = {}` 不能省

```cpp
struct Mat3 {
    double m[3][3] = {};
    ...
};
```

后面那个 `= {}` 把九个格子全部初始化为 0。不写的话，`Mat3 result;` 里是内存中的随机残留值——图形会莫名其妙，而且每次运行都不一样。

### 8.5 命名构造函数

```cpp
static Mat3 translation(double tx, double ty);
static Mat3 scaling(double sx, double sy);
static Mat3 rotation(double radians);
```

为什么不重载构造函数？因为 `Mat3(double)` 要表达三种意思时编译器无法区分。用静态成员函数给每种构造一个名字：`Mat3::rotation(angle)` 一眼就知道在做什么。

（定义时**不写** `static`：`Mat3 Mat3::rotation(...)` ✓，写成 `static Mat3 Mat3::rotation(...)` 会编译错误。）

### 8.6 矩阵乘法：内层 `k` 循环是本体

```cpp
result.m[row][col] = Σ_k a.m[row][k] * b.m[k][col];
```

每一格是"**A 的第 row 行**和 **B 的第 col 列**的点积"。注意 `k` 在 `a` 里是列下标、在 `b` 里是行下标——**这个共用的 `k` 正是把行和列缝在一起的那根线**。

去掉它、写成 `a.m[row][col] * b.m[row][col]`（逐元素相乘，数学上叫 Hadamard 积），结果会变成另一个东西，而且**编译不会报错**。M2 里踩过：所有组合变换的结果只与输入的 x 成正比，因为矩阵被压成了只剩一个对角元素。

### 8.7 顺序：`A · B` 表示"先做 B"

因为 `(A·B)·p = A·(B·p)`，括号里那个 `B·p` 先算。**读矩阵乘法要从右往左读**，像读复合函数 `f(g(x))`。

现场证据（`p = (1,0)`，绕 90° 的旋转 `R`，平移 `(5,0)` 的 `T`）：

- `R·T·p` = 先平移再旋转 = `(0, 6)`
- `T·R·p` = 先旋转再平移 = `(5, 1)`

**矩阵乘法不满足交换律**，在图形学里这不是抽象性质，而是"物体跑到不同位置"的真实差别。调试"位置不对"时，第一个要检查的就是乘法顺序。

### 8.8 浮点残差与容差比较

`cos(π/2)` 在数学上是 0，但在 double 里是 `6.12323e-17`，因为 `π/2` 本身存不下精确值。于是"把 (1,0) 转 90°"得到的是 `(6.12323e-17, 1)`，不是 `(0, 1)`。

规则：**浮点数不要用 `==` 比较，要用容差**（比如判断差值绝对值是否小于 `1e-9`）。M2 里"先平移再旋转"的结果是 `(3.67394e-16, 6)`，而 `6 × 6.12323e-17 = 3.67394e-16` ✓ 精确对得上——它确实是数学上的 `(0, 6)`，只是带着一个极小的残差。

## 第九部分 · 局部坐标与世界坐标（M2 最重要的思想）

八个方框是这样画出来的：

```cpp
// 局部坐标：方框的四角，中心在原点
const Vec2 local[4] = {
    Vec2(-halfSize, -halfSize),
    Vec2( halfSize, -halfSize),
    Vec2( halfSize,  halfSize),
    Vec2(-halfSize,  halfSize),
};

// 先绕自己的中心旋转，再搬到圆周上的位置
const Mat3 model = Mat3::translation(center.x, center.y) * Mat3::rotation(theta);

Vec2 world[4];
for (int j = 0; j < 4; ++j) {
    world[j] = transformPoint(model, local[j]);
}
```

**局部坐标**（也叫模型坐标）：原点在物体自己身上。这样定义的顶点数据又短又对称，而且**和它最终摆在画布哪里完全无关**。

**世界坐标**：物体在场景里的实际位置和朝向。中间的桥梁就是那个 `model` 矩阵。

这个分离带来三件事：

1. **一份顶点数据可以复用无数次。** 八个方框共用同一组 `local[4]`，只是各自乘了不同的矩阵。
2. **改摆放位置不用碰顶点数据。** 想让方框挪到别处、转个角度，只改矩阵，顶点表一个字不动。
3. **它是整条渲染管线的第一段。** M4 加载 OBJ 模型（顶点依然是局部坐标，用一个模型矩阵摆进场景）、M6 相机与投影（再加视图矩阵和投影矩阵）、骨骼动画（每个骨骼一个矩阵）——全是这条流水线的延伸。

也可以反过来说：**"顶点 × 矩阵"这个动作，就是你以后所有 3D 工作的最小单元。**

## 第十一部分 · 本次踩的六个坑

| # | 坑 | 教训 |
| --- | --- | --- |
| 1 | 函数签名里两个参数都叫 `b` | 命名冲突有时很难一眼看出，编译器指出的位置是准确的 |
| 2 | `y1` 写成 `lround(to.x)` | 一个字母的笔误能让算法"忠实地朝错误目标前进"；小画布 + 手算表把它逮住 |
| 3 | 两方向判断写成 `if / else if` | 语义相近的代码块，删掉一个 `else` 就改变了算法行为 |
| 4 | `translation` / `rotation` 没从单位矩阵出发 | 齐次坐标的 `m[2][2] = 1` 是硬性要求 |
| 5 | 矩阵乘法写成逐元素相乘 | 少一层循环，编译不报错，结果全错——最危险的一类 bug |
| 6 | 新建文件名大小写与 CMakeLists 不一致 | Linux 区分大小写；Windows 上侥幸通过，Linux 上直接失败 |

**共性**：这六个坑里，有三个（#2、#5、#6）**编译完全通过**，只是行为不对。它们全靠"打印中间结果 + 手算对照 + 差分对比"抓出来的。这就是为什么 M2 花了一整天在写测试，而不是写完画线就往下走。

## 第十二部分 · 自测题

1. `(0,0) → (5,2)` 的 `steps` 是多少？一共画几个像素？
2. 为什么 `steps` 取 `max(|dx|, |dy|)`，而不是只取 `|dx|`？
3. `std::lround` 和 `static_cast<int>` 的区别是什么？用错会怎样？
4. Bresenham 里为什么要把 `err` 乘 2？
5. 两个方向判断能不能写成 `if / else if`？为什么？
6. 差分测试里"理论点数 561"是怎么算出来的？
7. "不一致 6 个像素"说明什么？如果是 500 说明什么？
8. 2×2 矩阵为什么无法表示平移？
9. 齐次坐标里补上去的那个 1 起什么作用？
10. 仿射变换矩阵的 `m[2][2]` 必须是几？为什么？
11. `A · B` 表示"先做 A"还是"先做 B"？用哪个等式可以现场验证？
12. 为什么八个方框用 `T(center) · R(θ)` 而不是 `R(θ) · T(center)`？
13. 为什么标准旋转矩阵在屏幕上看起来是顺时针？
14. 把顶点定义在局部坐标里，比直接写世界坐标好在哪里？

### 参考答案

1. `steps = max(5, 2) = 5`，画 `steps + 1 = 6` 个像素。
2. 因为要"沿长轴每步走一格"。只按 `|dx|` 算，陡线每步 y 会跳很多格，线变成断续的点。
3. `lround` 四舍五入，`static_cast<int>` 截断。截断会让整条线偏左上半个像素。
4. 原判据要跟"一半"（0.5）比较，会引入小数；乘 2 之后全部变成整数比较。
5. 不能。45° 附近两条同时成立，一次要往两个方向各走一步（斜角步），`else if` 会让斜角步永不发生。
6. `dx = 600 − 40 = 560`、`dy = 315 − 30 = 285`，`steps = max = 560`，点数 `steps + 1 = 561`。
7. 6 个说明两个实现都对，只是在"理想高度正好半格"的位置取整方向不同；500 说明有一个实现画错了。
8. 因为 2×2 变换必定把原点 `(0,0)` 映射到原点，而平移的本质就是把原点挪走。
9. 它让矩阵第三列的平移量在乘法中真正参与运算（`x' = 1·x + 0·y + tx·1`）。
10. 必须是 1。否则齐次坐标第三行算出的 `w = 0`，`transformPoint` 里的除法失效，结果全废。
11. 先做 B。因为 `(A·B)·p = A·(B·p)`，括号里的 `B·p` 先算。验证方法：比较 `transformPoint(A*B, p)` 与 `transformPoint(A, transformPoint(B, p))`。
12. 因为要"先让方框绕自己的中心转，再把它搬到圆周上"。反过来写就变成"先搬到位置上，再绕画布原点转"，八个方框会被甩散。
13. 因为画布的 y 轴朝下，整个坐标系相对数学坐标被上下镜像了。想视觉上逆时针就传负角度。
14. 顶点数据与摆放位置/朝向解耦：一份数据可以配任意多个矩阵重复使用，改位置不用改顶点表。这也是整条渲染管线（模型矩阵 → 视图矩阵 → 投影矩阵）的组织方式。
