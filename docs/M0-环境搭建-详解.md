# M0 环境搭建 · 详解版

> 本文假设你没有 Linux、操作系统、版本控制的任何基础。
> 每个名词都会拆开解释，不依赖任何前置知识。

## 1. 为什么要有两台系统，文件到底存在哪

### 1.1 什么是虚拟机

你的 Windows 电脑是**物理机**，真实存在的硬件。
Ubuntu 装在 VMware 里，是**虚拟机**——由软件模拟出来的一台"电脑"。

它有虚拟的 CPU、内存、硬盘、网卡。对 Ubuntu 来说，它以为自己是真电脑；
对你的 Windows 来说，Ubuntu 只是几个文件（`D:\VM\Ubuntu24\` 下那些 `.vmdk`
就是它的"硬盘"）。两台电脑同时运行，各跑各的系统。

### 1.2 为什么必须用 Linux

你以后要做的网络编程、系统编程，核心概念都是 **Linux 独有**的：
epoll、进程、文件描述符、信号。Windows 上根本没有对应的东西。

企业里服务器 99% 是 Linux，面试问的全是这一套。在 Windows 上学，
等于学了一半，而且学了用不上。

### 1.3 为什么还留着 Windows

因为你的日常工具都在 Windows 上：Visual Studio、浏览器、加速器。
图形界面更好用，编辑代码更舒服。于是有了这个分工：

| 做什么 | 在哪 |
|---|---|
| 编辑代码 | Windows（顺手） |
| 编译、运行、调试 | Ubuntu（正确） |

### 1.4 关键点：全世界只有一份文件

    D:\Users\MONEY\Desktop\渲染器项目\code\src\main.cpp   ← Windows 视角
    /mnt/hgfs/code/src/main.cpp                            ← Ubuntu 视角

**这不是两份文件，是同一份文件的两个门牌号。**

在 Ubuntu 里改一行，Windows 里那个文件立刻变，反过来也一样。
因为它们压根就是同一个东西，只是从两条不同的路走进去。

### 1.5 路径为什么长得完全不同

| 系统 | 写法 | 特点 |
|---|---|---|
| Windows | `D:\Users\...` | 反斜杠 `\`，以盘符开头 |
| Linux | `/mnt/hgfs/code` | 正斜杠 `/`，以根 `/` 开头 |

两个系统的"地址书写规则"不同，就像中文地址和英文地址写法不同，
但可能指向同一个地方。

## 2. 挂载是什么

### 2.1 什么是文件系统

硬盘上存着几百万个文件，它们不能乱堆，必须有组织方式：谁在哪个目录下、
文件从哪个字节开始、占多大、谁能读谁能写。这套组织规则叫**文件系统**。

你在资源管理器里看到的目录树，就是文件系统给你的那层视图。
底下的字节怎么摆，你平时看不到也不需要看到。

### 2.2 什么是路径

路径就是"怎么走到那个文件"：从某个起点出发，一层层往下。

### 2.3 Windows 是"多棵树"，Linux 是"一棵树"

这是两种系统最根本的观念差异，也是你困惑的根源。

**Windows：每个盘一棵独立的树**

    C:\  →  一棵树（Program Files、Windows、Users...）
    D:\  →  另一棵树（VM、Games...）
    E:\  →  第三棵

三棵树互不相干，所以 Windows 需要"盘符"来区分它们。

**Linux：全世界只有一棵树**

    /                      ← 唯一的根
    ├── bin/               系统命令
    ├── etc/               配置文件
    ├── home/
    │   └── heshuyan/      你的家目录，~ 就是它
    ├── mnt/               约定的挂载点目录
    │   └── hgfs/          ← 共享文件夹挂在这里
    ├── usr/               软件
    └── var/               运行数据

**没有 C 盘 D 盘。** 所有存储设备都在这棵树里找位置。

### 2.4 那插进来的 U 盘怎么表示？

Linux 的做法：**在树上找一个空目录，把 U 盘接到那儿。**

这个动作叫**挂载**（mount），那个空目录叫**挂载点**（mount point）。

挂载点像墙上的插座孔，文件系统像插头。
孔本身什么都没有；插上之后，那个位置才通了电。

### 2.5 /mnt/hgfs 到底是什么

- `/mnt` —— mnt 是 mount 的缩写，Linux 约定把挂载点放这里
- `/mnt/hgfs` —— 挂载之前是**空的**，只是一个"插座孔"
- 挂载之后 —— 它"变成"了 Windows 上 `code` 文件夹的样子

所以 `/mnt/hgfs/code/src/main.cpp` 的正确读法是：

> 在虚拟机唯一的那棵树上，透过挂在 `/mnt/hgfs` 的共享通道，
> 走进里面叫 `code` 的文件夹，再进 `src`，找到 `main.cpp`。
> 而这个 `code`，其实就是你 Windows 桌面上的那个文件夹。

### 2.6 vmhgfs-fuse 命令逐词拆解

    sudo vmhgfs-fuse .host:/ /mnt/hgfs -o allow_other -o uid=$(id -u) -o gid=$(id -g)

| 部分 | 含义 |
|---|---|
| `sudo` | 以管理员身份运行。挂载是系统级操作，普通用户没权限 |
| `vmhgfs-fuse` | 程序名。作用是把 VMware 共享变成 Linux 目录 |
| `.host:/` | 挂载源。`.host:` 是 VMware 定的名字，代表宿主机；`/` 是共享的根 |
| `/mnt/hgfs` | 挂载点，接到树上哪个位置 |
| `-o allow_other` | 允许 root 以外的用户访问 |
| `-o uid=$(id -u)` | 把挂进来的文件属主设为你。`id -u` 输出你的数字用户 ID（1000） |
| `-o gid=$(id -g)` | 同上，用户组 |

`-o` 可以写多次，每次带一个选项。

### 2.7 为什么 mount -t vmhgfs 会失败

    sudo mount -t vmhgfs .host:/ /mnt/hgfs

报 `未知的文件系统类型"vmhgfs"`。

原因：`mount` 只负责"挂载"这个动作本身，具体某种文件系统怎么读怎么写，
要靠内核里对应的**驱动模块**。老版 Ubuntu 有个叫 `vmhgfs` 的内核模块干这事，
但 Ubuntu 24.04 已经把它移除了。

替代方案是把这份工作搬到**用户态**做，也就是 FUSE
（Filesystem in USErspace，用户空间文件系统）。`vmhgfs-fuse` 就是它的实现。

所以不是你配错了，是**方案换代了**。

## 3. fstab 六字段详解

### 3.1 问题：挂载是运行时状态，重启就没了

手动执行 `vmhgfs-fuse` 之后，挂载只存在于**当前这次开机期间**。
一重启，内核重新初始化，这条记录就没了，`/mnt/hgfs` 又变回空目录。

所以需要一个"开机自动执行挂载"的机制。

### 3.2 fstab 是什么

`/etc/fstab`（file system table，文件系统表）就是开机挂载清单。
系统启动时读它，把里面每一条挂载都执行一遍。

我们加的那一行：

    .host:/  /mnt/hgfs  fuse.vmhgfs-fuse  allow_other,defaults,nofail,uid=1000,gid=1000  0  0
       ①        ②              ③                            ④                          ⑤ ⑥

### 3.3 六个字段逐个

**① 设备：挂什么**
`.host:/` 代表 VMware 共享根。也见过 `/dev/sda1` 这种，表示某块硬盘的某个分区。

**② 挂载点：挂到哪**
`/mnt/hgfs`，必须是已存在的目录。

**③ 文件系统类型**
`fuse.vmhgfs-fuse`。格式为 `fuse.程序名`，意思是"这个挂载由 vmhgfs-fuse 负责"。

**④ 挂载选项**（逗号分隔，可多个）
- `allow_other` 允许 root 以外的用户访问
- `defaults` 一组默认选项的简写，含 rw（可读写）、exec（可执行）等
- `nofail` **挂载失败也不阻塞开机**
- `uid=1000,gid=1000` 文件属主

**⑤ dump 标志**
备份工具用，现代系统无人关心，填 `0`。

**⑥ fsck 检查顺序**
开机自检顺序：根分区填 1，其他填 2，`0` 表示不检查。网络挂载必须填 0。

### 3.4 为什么 nofail 重要

如果某条挂载失败又没写 `nofail`，系统会认为"有设备没挂上"，
可能掉进紧急修复模式，或者卡在半路开不了机。

网络共享本质上不稳定：VMware 工具没启动、共享配置被改，都可能失败。
`nofail` 就是告诉系统：挂不上就算了，照常开机。

### 3.5 为什么用 tee 而不是 >>

最自然的写法应该是：

    sudo echo '.host:/ /mnt/hgfs ...' >> /etc/fstab

**这条命令会失败。** 这是新手最容易掉进去的坑，原因值得慢慢讲。

shell 执行命令前会**先处理重定向**：

1. 先由**你当前的用户**（不是 root）打开 `/etc/fstab`，准备追加写入
2. 再执行 `sudo echo ...`
3. 把 echo 的输出写进第 1 步打开的文件

问题在第 1 步：你有权开 `/etc/fstab` 吗？没有。shell 直接报 `Permission denied`，
`sudo` 根本还没轮到上场。

**sudo 只能提权它后面那条命令，提权不了 shell 的重定向动作。**

正确写法用管道，把提权交给真正写文件的程序：

    echo '...' | sudo tee -a /etc/fstab

- `tee` 从标准输入读数据，同时写到文件和屏幕
- `-a` = append，追加而非覆盖
- `sudo tee -a /etc/fstab` 整体被提权执行，所以它能写

### 3.6 umount 和 mount -a

- `sudo umount /mnt/hgfs` —— 卸载。注意拼写是 `umount`（少一个 n），历史遗留
- `sudo mount -a` —— 按 fstab **全部**条目挂载一遍，用来验证 fstab 写对没有

我们当时的验证：先卸载，再 `mount -a`，能重新挂上就说明那行有效。

## 4. g++、make、CMake 各自干什么

### 4.1 从源码到程序，中间有四步

    main.cpp
       ↓  预处理：处理 #include、#define，把宏展开
    展开后的源码
       ↓  编译：C++ 代码 变成 汇编代码
    汇编代码
       ↓  汇编：汇编 变成 机器码
    main.o          ← 目标文件，单独还不能运行
       ↓  链接：把 .o 和标准库拼到一起
    app             ← 可执行文件，终于能跑

### 4.2 g++ 一个人干了四件事

`g++` 是"编译器驱动"，它内部会依次调用预处理器、编译器、汇编器、链接器。
所以你可以只敲一条 `g++ main.cpp -o app` 就得到成品。

### 4.3 为什么不能一直手敲 g++

三个原因：

1. **命令会失控。** 十个 `.cpp` 手敲十次？改一个头文件全部重敲？
2. **没有增量编译。** 只想重编改动过的文件，手敲做不到。
3. **参数和平台差异。** 编译选项散在脚本里，迟早失守。

### 4.4 make 是干什么的

`make` 读一个叫 `Makefile` 的文件。里面写的是一张依赖表：

    目标: 依赖
        命令

make 会比对文件时间戳：依赖比目标新，才执行命令。这样天然实现增量编译。

### 4.5 CMake 是干什么的

CMake 读你写的 `CMakeLists.txt`，**生成 Makefile**。

为什么不直接写 Makefile？
- Makefile 语法晦涩，缩进用 Tab 这种坑一堆
- 跨平台差，Windows 和 Linux 的 Makefile 写法不同

CMake 的定位叫"构建系统生成器"：**它不编译代码，它生成编译规则。**

### 4.6 三者关系

    CMakeLists.txt  --cmake-->  Makefile  --make-->  g++  -->  app
       （你写的）              （自动生成）        （真正干活）

### 4.7 对照你敲的三条命令

| 命令 | 实际含义 |
|---|---|
| `cmake -S /mnt/hgfs/code -B ~/build-renderer` | 读源码目录的 CMakeLists.txt，在构建目录生成规则表 |
| `cmake --build ~/build-renderer` | 按规则表干活，也就是让 make 去调 g++ |
| `~/build-renderer/app` | 运行最终产物 |

## 5. 为什么 -S 和 -B 不能是同一个目录

### 5.1 两个目录的角色

- `-S`（source）：**你手写的文件**放哪
- `-B`（build）：**机器生成的文件**放哪

### 5.2 混在一起的坏处

如果都指向源码目录，CMake 会把几百个生成文件吐在你的源码旁边：

- `CMakeCache.txt`、`CMakeFiles/`、`Makefile`、`cmake_install.cmake` 全混进来
- `git status` 一片红，你分不清哪些是你写的、哪些是机器生成的
- 想重新来一遍得手工删一堆东西，还容易删错

分开之后，清理只需要删掉整个构建目录，源码一根汗毛都不动。

### 5.3 对我们来说更重要的原因：FUSE 慢

共享文件夹不是真硬盘，它是 FUSE 文件系统。每读写一次要走：

    程序 → Linux 内核 → FUSE → VMware 工具 → Windows → 虚拟磁盘 → 真实硬盘
                                （原路返回）

一个来回穿七八层。手工改一个文件感觉不出来；但编译会生成**上百个小文件**，
每个都走一趟，累加起来就非常慢。

所以规矩是：**源码放共享文件夹（你方便编辑），构建产物放虚拟机本地（编译快）。**

## 6. 终端命令语法基础

### 6.1 命令的构成

    命令名  选项  参数
    cmake   -S    /mnt/hgfs/code

空格分隔。命令名是程序名，后面是给它的东西。

### 6.2 路径：绝对路径与相对路径

- **绝对路径**：以 `/` 开头，从树根开始写。如 `/mnt/hgfs/code`。在哪执行都一样
- **相对路径**：不以 `/` 开头，从"当前所在目录"开始。如 `docs/M0.md`

两个特殊符号：

- `.` 表示当前目录
- `..` 表示上一级目录

所以 `cd ..` 是"回到上一层"。

### 6.3 sudo 与权限

Linux 是多用户系统，每个文件都有属主和权限。
`root` 是超级用户，能改任何东西。

`sudo`（superuser do）的意思是：**这一条命令临时以 root 身份执行**。
改系统配置、装软件、动 `/etc` 下的文件，都要用它。

用完就恢复成你自己，不会一直有超级权限——这是安全设计。

### 6.4 选项的两种写法

- 短选项：`-S`、`-y`、`-a`，一个字母
- 长选项：`--build`、`--public`，通常更好读

两者常常是等价的，比如 `-S` 和 `--source`。

有些选项要带值，写成 `-o allow_other` 或 `-o=allow_other`。

### 6.5 重定向

- `>` 把输出写进文件，**覆盖**原内容
- `>>` 把输出写进文件，**追加**在后面
- `<` 从文件读入

默认情况下命令的输出是打到屏幕上的，重定向就是"改打到文件里"。

### 6.6 管道 |

    echo '...' | sudo tee -a /etc/fstab

管道把**左边命令的输出**，当作**右边命令的输入**。
像水管一样把两个程序接起来。

### 6.7 命令替换 $(...)

    -o uid=$(id -u)

shell 会先执行括号里的 `id -u`，拿到它的输出（1000），
把结果填进这个位置，然后才执行整条命令。

### 6.8 其他常用符号

| 符号 | 含义 |
|---|---|
| `~` | 家目录，即 `/home/heshuyan` |
| `&&` | 左边成功才执行右边 |
| `*` | 通配符，匹配任意文件名，如 `*.cpp` |
| `Ctrl+C` | 中止当前正在运行的命令 |
| `Tab` | 自动补全路径或命令名，能省很多打字 |

## 7. git 的四个区域

### 7.1 为什么需要版本控制

没有版本控制时，改代码是这样的：

    最终版.cpp
    最终版2.cpp
    最终版_真的最终.cpp
    最终版_备份_别删.cpp

版本控制解决四件事：
1. 每次改动都有记录，能看、能回退
2. 能对比"这次和上次差在哪"
3. 多人协作不会互相覆盖
4. 代码有云端备份

### 7.2 两个核心概念

- **仓库（repository）**：被 git 管理的文件夹。里面有个隐藏的 `.git` 目录，
  存放全部历史记录。删掉 `.git`，这个文件夹就变回普通文件夹了
- **提交（commit）**：一次"快照"。它记录"此刻这些文件长什么样"，
  附带作者、时间、说明

### 7.3 四个区域

    工作区            暂存区           本地仓库          远程仓库
  (你编辑的文件)   (待提交清单)    (.git 里的历史)   (GitHub 服务器)
       │                │               │                │
       │   git add      │               │                │
       ├───────────────>│               │                │
       │                │  git commit   │                │
       │                ├──────────────>│                │
       │                │               │    git push    │
       │                │               ├───────────────>│
       │                │               │                │
       └──── 全在你自己硬盘上 ──────────┘      ↑ 只有这一步需要网络

### 7.4 add 和 commit 到底差在哪

这就是**前两个区域**的差别：

- `git add` 是"我把这些改动挑出来，放进待提交清单"
- `git commit` 是"把清单里的东西正式存进历史记录"

为什么要有暂存区这层？因为一次改动可能包含好几件互不相关的事，
你可以挑一部分先提交。但即使你懒得挑，直接 `git add .` 加全部再用 `git commit`，
这两步仍然是两个独立动作。

**没 add 就 commit，git 不知道你想提交什么**，于是你会看到
"提交为空，但是存在尚未跟踪的文件"——你当时遇到的那句。

### 7.5 .gitignore

一个文本文件，里面列的文件名/目录会被 git **完全无视**，
不跟踪、不提示、不提交。

我们写的内容：

    build/      编译产物
    out/        Visual Studio 生成的
    .vs/        Visual Studio 生成的
    .vscode/    VS Code 生成的
    *.tga       后面生成的图片
    *.ppm       后面生成的图片

凡是"机器生成的、可以随时重新做出来的"，都不该进仓库。

### 7.6 core.fileMode 那条配置

    git config core.fileMode false

git 会记录每个文件的可执行权限（能不能直接运行）。
但共享文件夹在两个系统之间对权限的理解不一致，会导致 git 频繁误报
"某某文件被修改了"，可你明明一个字没动。

关掉这个检测就清静了。这是共享文件夹 + git 的标准配置。

## 8. 分支与 commit / push 的区别

### 8.1 分支是什么

分支就是一条**独立的提交链**。默认从主线上分出来，
你在分支上的改动不影响别的分支。

个人项目里通常只用一条主线，所以你现在只需要知道：
**分支是个名字，用来标识"我们现在在哪条线上"**。

### 8.2 为什么叫 main

git 早期默认分支名是 `master`，2020 年起业界普遍改用 `main`
（更中性，GitHub 也把默认值改成了 `main`）。

你截图里那句"提示：使用 'master' 作为初始分支的名称"不是错误，
是 git 在告诉你它的默认值，并建议你改。我们改成了 `main`，
并且用 `git config --global init.defaultBranch main` 让**以后建的仓库也默认用 main**。

### 8.3 commit 和 push 的区别

| | commit | push |
|---|---|---|
| 做了什么 | 存进**本地**仓库 | 把本地记录同步到**远程**仓库 |
| 在哪 | 你自己硬盘上的 `.git` | GitHub 服务器 |
| 需要网络吗 | **不需要** | **需要** |
| 能不能撤销 | 能，本地操作随便改 | 麻烦，别人可能已经拉走了 |

一句话：**commit 是存档，push 是上传。**

### 8.4 remote 和 origin

- `remote` 是"远程仓库地址"的登记项
- `origin` 是这条登记项的名字，也就是**默认的远程仓库别名**

`git push` 不带参数时，git 会找当前分支对应的远程——也就是 `origin`。

你当时那句 `fatal: 没有配置推送目标`，就是因为那会儿还没有任何远程仓库被登记。
后来 `gh repo create` 帮我们做了两件事之一：`git remote add origin <地址>`。

### 8.5 本地和远程可以不一致

你现在的仓库就是这样：本地有 3 个提交，GitHub 上有 2 个。
这完全正常——第三个还没 push 上去。

**本地多出来的提交是安全的**，它们存在你硬盘的 `.git` 里。
等网络通了，push 一次就追上去了。

## 9. gh auth login 授权时发生了什么

### 9.1 为什么需要授权

GitHub 上的仓库是你的私有财产，服务器必须确认"来推代码的这个人真的是你"。

### 9.2 为什么不用密码

GitHub 早就禁用密码做 git 操作了。原因：

- 密码一旦泄露，攻击者能做任何事
- 密码权限太大，没法限制范围、没法单独撤销

替代方案是**令牌（token）**：一串随机字符，可以限定权限、可以随时作废。

### 9.3 OAuth 设备授权流程

`gh auth login` 用的是"设备授权"，专门为**没有浏览器的设备**设计
（比如你的虚拟机、服务器）。流程是：

1. gh 向 GitHub 申请授权，GitHub 返回一个**一次性验证码**
2. gh 把码显示在终端，让你去浏览器打开 `github.com/login/device`
3. 你在网页上输入这个码，确认授权
4. GitHub 通知 gh："这个人同意了"
5. gh 拿到令牌，存进本地凭据存储

**关键点：你的密码从头到尾没有经过 gh 和虚拟机。**
网页登录是你在浏览器里跟 GitHub 完成的，gh 只拿到"已授权"这个结果。
这就是为什么这个过程是安全的。

### 9.4 之后 push 为什么不用输密码

gh 拿到令牌后，还会替你配置 git 的凭据助手，
把令牌存进系统的凭据管理里。之后 git 需要认证时，自动去取。

**不是它记住了你的密码，而是 GitHub 给了它一把钥匙。**

## 10. 为什么 commit 不需要网络，push 才需要

回到第 7 节的四区图：

    git add     → 只动你自己硬盘上的文件
    git commit  → 只往你自己硬盘的 .git 里写记录
    git push    → 这才需要跟 GitHub 服务器通信

前面两步跟网络**一点关系都没有**。所以断网也能正常写代码、正常提交，
攒够了一次性推。

### 10.1 我们实测到的网络情况

| 环境 | 结果 |
|---|---|
| 虚拟机（NAT） | 直连 github.com:443 超时，21 秒 |
| 主机（加速器关闭） | 同样超时，21 秒 |
| 主机（加速器开启） | 推送成功 |

结论：**直连是不通的，必须开加速器。**

### 10.2 虚拟机为什么用不上主机的加速器

虚拟机的网络是 NAT 模式：它把你的主机当路由器，直接往外发请求。
主机上运行的加速器只是个**本机程序**，默认不接管虚拟机的流量。

所以虚拟机里的 git push 必然超时。

### 10.3 因此定下的工作流

| 环节 | 在哪做 |
|---|---|
| 编辑代码 | Windows（Visual Studio） |
| 编译、运行、调试 | Ubuntu |
| git add / git commit | Ubuntu（本地操作，不需要网络） |
| git push | Windows（GitHub Desktop 点 Push origin） |
