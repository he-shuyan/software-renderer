## 第一部分 · 全景：模型文件就是两张表

打开任何一个三维模型文件，核心内容都是：

**顶点表**：一串三维坐标。
**面表**：每行记几个顶点**编号**，表示"这几个点围成一个三角形"。

**为什么用编号而不是直接写坐标？** 两层原因：

1. **省空间。** 一个立方体只有 8 个顶点，却要组成 12 个三角形。如果每个三角形各写一遍自己的三个坐标，就是 36 个点，其中大量重复。
2. **省计算。** 用索引时每个顶点只存一份，所以"变换顶点""计算光照"这类操作**每个顶点只需要算一次**，而不是每个三角形算三次。一个十万面的模型，这一项能省下几十万次运算。

于是有了"顶点数组 + 索引数组"这套结构。GPU 吃的也是这种数据（OpenGL 里对应 `glDrawElements`）。

## 第二部分 · `Vec3` 与"要不要模板化"

`Vec3` 就是把 `Vec2` 加一个分量，代码几乎逐行对应。

值得记下的是**这次没做的决定**：把 `Vec2` 和 `Vec3` 合并成一个模板 `Vec<N>`，听起来更"优雅"，但代价是：

- 模板的错误信息会变得难以阅读；
- 以后真的需要 `Vec4` 时，往往还要写特化代码，复杂度又回来了；
- 而现在两个类型加起来不到八十行，任何人打开文件都能一眼看完。

**抽象是有成本的投资，应该由"重复带来的真实痛苦"来触发，而不是由"看起来更优雅"来触发。** 等 M6 需要四维向量时再重新判断。

## 第三部分 · 右手坐标系与三轴旋转

### 3.1 右手坐标系

我们约定模型空间为**右手坐标系**：x 向右、y 向上、z 朝向观察者。

"右手"这个词来自判断旋转方向的方法：**右手拇指指向旋转轴的正方向，四指弯曲的方向就是正角度的转向**。这套约定和 OpenGL 一致，以后学相机矩阵时可以直接接上。

### 3.2 三个旋转矩阵

```
rotationX:  [1   0    0 ]      rotationY:  [ c  0  s ]      rotationZ:  [c  -s  0]
            [0   c   -s ]                  [ 0  1  0 ]                  [s   c  0]
            [0   s    c ]                  [-s  0  c ]                  [0   0  1]
```

**记忆方法：绕哪根轴转，那一行（和同一列）保持"单位向量"。** 绕 x 转时 x 不变，所以第 0 行是 `1 0 0`；绕 y 转时 y 不变，第 1 行是 `0 1 0`；绕 z 转时 z 不变，第 2 行是 `0 0 1`。

**为什么旋转部分缩在那 2×2 里？** 因为旋转轴上的分量不参与旋转——它只是"原地转圈"。

**顺便看清一件事：** 我们在 M2 写的 `Mat3::rotation` 就是这里的 `rotationZ`。**二维旋转其实是"绕 z 轴旋转"的特例**——当时不需要 z，现在我们终于看清了它的位置。

### 3.3 手算验证（每次写旋转都要做）

| 操作 | 预期结果 |
| --- | --- |
| `rotationX(90°)` 作用在 `(0,1,0)` | `(0, 0, 1)` —— y 转到 z |
| `rotationY(90°)` 作用在 `(1,0,0)` | `(0, 0, −1)` —— x 转到 −z |
| `rotationZ(90°)` 作用在 `(1,0,0)` | `(0, 1, 0)` —— x 转到 y |

用右手定则自己比划一遍，比读十遍代码有用。屏幕上会出现 `6.12e-17` 这类残差，那是 `cos(90°)` 在 double 里的存储误差（M2 已经讲过）。

## 第四部分 · `transformPoint` 与 `transformVector`

两个函数都是"矩阵乘一个东西"，但语义完全不同：

| | 输入 | 补不补 `1` | 除不除 `w` | 受平移影响 |
| --- | --- | --- | --- | --- |
| `transformPoint` | `Vec2` | 补 `(x, y, 1)` | 除以 w | **会** |
| `transformVector` | `Vec3` | 不补 | 不除 | **不会** |

**为什么？** 因为"点"是位置，"向量"是方向和长度。把原点平移到别处，一个点会跟着移动，但"从原点指向 (1,0,0) 的方向"没有任何变化。

这个区分在图形学里非常关键，最典型的例子是**法线变换**（M8）：

> 法线是方向，不是位置。**如果误用 `transformPoint` 去变换法线，模型一平移，光照就全错了。**

命名本身就承载了这个区分——如果两个函数都叫 `transform`，三个月后你一定会用错。

## 第五部分 · OBJ 文件格式

### 5.1 我们关心的标记

```
# 这一行是注释
v -1 -1 -1              ← 顶点：三个浮点数
vn 0 0 1                ← 法线（M4 跳过）
vt 0.5 0.5              ← 纹理坐标（M7 才用）
f 5 6 7                 ← 面：三个顶点索引
f 1/2/3 4/5/6 7/8/9     ← 带纹理与法线索引的写法
```

### 5.2 三条必须记住的规则

**第一，索引从 1 开始。** `f 5 6 7` 里的 5 指的是**第 5 个 `v` 行**，对应 C++ 里的 `vertices[4]`。所以读进来必须 `- 1`。

漏掉这个减一，整个模型会"错位一格"——顶点之间的连接关系全乱，画出来是一团纠缠的线。这是 OBJ 解析里最经典的坑，也是最有价值的一条测试（顶点数、面数都对，但图形完全错乱）。

**第二，一个面可以有任意多个顶点。** 三角形、四边形、五边形都会出现（很多建模软件默认导出四边形）。程序必须能把它们拆成三角形。

**第三，绕序决定朝向。** 顶点顺序（比如 `5 → 6 → 7` 还是 `5 → 7 → 6`）表示这个面的正反。约定是"从物体外面看逆时针"。判断方法：`(v1−v0) × (v2−v0)` 得到的向量就是法线方向，它应当指向物体外侧。

M4 只画线框，顺序错了看不出来；但 **M5 的背面剔除、M8 的光照都要靠它**。写模型文件时顺手写对，后面少一堆难查的怪现象。

## 第六部分 · 解析器：三层结构

```
文件  →  一行  →  一个个单词
ifstream → getline → istringstream
```

### 6.1 打开文件

```cpp
std::ifstream in(path);
if (!in) {
    return false;
}
```

`std::ifstream` 是输入文件流。**构造函数直接尝试打开，失败时不会抛异常，而是把流置为失败状态**，所以紧跟一句 `if (!in)` 判断。这和 `saveBMP` 里那句是同一个模式——读写文件的标准起手式。

### 6.2 逐行读取

```cpp
std::string line;
while (std::getline(in, line)) { ... }
```

`std::getline` 读一行到字符串，**到达文件末尾时返回假**，循环自然结束。不需要自己数行数或处理换行符。

### 6.3 把一行当输入流

```cpp
std::istringstream iss(line);
std::string tag;
iss >> tag;
```

`std::istringstream` 把字符串包装成输入流，于是你可以用完全一样的 `>>` 语法从这一行里取值。**这是 C++ 解析文本最省事的办法**：

- `>>` 自动跳过任意多个空格和制表符；
- 读 `double` 时能正确解析 `-1`、`0.5`、`1e-3`、`-1.0`；
- 不需要自己写任何字符串切分代码。

**"宽容解析"**：我们只处理 `v` 和 `f`，其它标记一律不动。所以注释行、`vn`、`vt`、空行、甚至以后出现的 `mtllib`、`usemtl`，都会被自动跳过，不会报错。真实模型文件里的标记比我们用的多得多，这种写法让解析器天然健壮。

### 6.4 面的处理：斜杠与三角化

```cpp
while (iss >> token) {
    const std::size_t slash = token.find('/');
    const std::string first = (slash == std::string::npos)
                                  ? token
                                  : token.substr(0, slash);

    indices.push_back(std::stoi(first) - 1);
}
```

- `std::string::find('/')` 返回斜杠的位置；**找不到时返回 `std::string::npos`**（一个特殊的极大值，表示"无此位置"）。判断"找到没找到"必须和它比较，不能和 `-1` 比。
- `token.substr(0, slash)` 取从 0 开始、长度为 `slash` 的子串，也就是斜杠之前的部分。
- `std::stoi(...)` 把字符串转成整数（"string to int"）。

然后三角化：

```cpp
for (std::size_t i = 1; i + 1 < indices.size(); ++i) {
    model.faces.push_back(Face{indices[0], indices[i], indices[i + 1]});
}
```

以第 0 个顶点为中心做**扇形拆分**：n 个顶点的面拆成 n−2 个三角形。三角形（n=3）只产生一个；四边形产生两个；五边形产生三个。

**"任何多边形都能拆成三角形"这句话，在 M3 是理论，在这里变成了七行代码。**

## 第七部分 · 加载器的错误策略

```cpp
bool loadObj(const std::string& path, Model& model);
```

**为什么返回 `bool` 而不是直接返回 `Model`？** 因为需要区分两种情况：

- 加载失败（文件不存在、格式错、索引越界）；
- 加载成功但模型是空的（合法的空文件）。

如果只返回 `Model`，调用方无法区分这两者。返回 `bool` + 引用输出参数，是文件读取函数的标准做法。

**校验放在加载器里，而不是交给调用方。**

```cpp
// loadObj 末尾
for (const Face& face : model.faces) {
    if (face.a < 0 || face.a >= vertexCount || ...) {
        return false;
    }
}
```

这样"加载成功"就等价于"模型可用"，调用方拿到 `true` 之后不必再提心吊胆地检查索引。"把校验放在最靠近数据入口的地方"是一条通用原则：**入口把关一次，下游安心一路。**

## 第八部分 · 投影：从三维到二维

### 8.1 正交投影

M4 用的是最朴素的**正交投影**：旋转之后，直接把 `(x, y)` 当作画布坐标，**把 z 丢掉**。

它的特点是"远处的物体和近处的一样大"——因为没有用到 z 做缩放。这在工程图、建筑图里很常见（也叫轴测图），但不符合人眼看世界的方式。

**透视投影**才是"近大远小"，它的做法是把 x、y 除以（与 z 相关的）`w`——这正是 M2 里那个 `w` 除法预留的位置。M6 会用 4×4 矩阵把它正式接上。

### 8.2 为什么要把 y 取反

模型空间是右手系（**y 向上**）；画布是屏幕坐标系（**y 向下**）。同一个数值，在一个里表示"更高"，在另一个里表示"更靠下"。

所以投影时必须取反：

```
画布 y = 中心 y − 模型 y × 缩放
```

漏掉这个负号，整个模型会上下颠倒。这不是 bug，而是坐标系约定转换时必然出现的一步。（M6 做投影矩阵时，会把这个负号写进矩阵里。）

## 第九部分 · 归一化：让任何模型都能显示

### 9.1 为什么要归一化

写死缩放的代码只能对付"坐标范围大约 ±1"的模型。换一个模型：

- 范围 ±100 的 → 画到画布外面，只露出几个角；
- 范围 0.001 的 → 缩成一个看不见的点。

正确做法是**先量尺寸，再决定怎么摆**。

### 9.2 两遍扫描

```
第一遍：遍历所有顶点，求出投影后的包围盒
第二遍：投影并画线
```

这也是图形工具里常见的结构：**先量、再画**。代价是顶点被变换了两次，多花一点点时间；想省的话可以在第一遍把变换结果存进一个 `std::vector<Vec2>` 复用。**先正确，再优化。**

### 9.3 求包围盒的 `first` 技巧

包围盒的初值**不能设成 0**：如果模型整体位于 `x > 100` 的区域，用 0 起手会把 `minX` 污染成 0，模型会被错误地缩小并偏移。

正确做法是"用第一个元素初始化，后面再逐步比较"：

```cpp
if (first) {
    minX = maxX = px;
    minY = maxY = py;
    first = false;
} else {
    minX = std::min(minX, px);
    ...
}
```

这是求最值时的标准套路，值得记住。

### 9.4 等比缩放

```cpp
const double scale = std::min(image.width() * margin / modelW,
                              image.height() * margin / modelH);
```

分别算出"按宽度铺满需要放大多少倍"和"按高度铺满需要放大多少倍"，**取小的那个**：

- 取小的 → 两个方向都能装下；
- 两个方向**共用同一个倍数** → 不会被拉伸变形。

如果 x 用一个倍数、y 用另一个，立方体会变成砖头。**"取 min 保证装得下，共用倍数保证不变形"**，这两句可以一起记。

### 9.5 退化保护

```cpp
if (modelW <= 0.0 || modelH <= 0.0) {
    return;
}
```

如果所有顶点投影后落在一条线上，宽或高就是 0，后面的除法会得到 `inf` 或 `NaN`，画出来一片乱。这和之前写过的三次防御（缓冲区大小、退化三角形、边界检查）是同一类：

> **凡是"用算出来的数做除数"，先问一句"它可能是 0 吗"。**

## 第十部分 · 线框上的对角线是怎么回事

M4 渲染出来的立方体里，除了 12 条棱边，还多出 6 条斜线。**这不是 bug**，而是"三角形网格线框"的必然外观。

原因：`cube.obj` 的每个四边形面都写成了两个三角形，例如前面是 `f 5 6 7` 和 `f 5 7 8`。这两个三角形共享边 `5-7`——这就是三角化时产生的对角线。线框渲染把**每个三角形的三条边**都画出来，所以这条对角线也被画了。

六个面各产生一条对角线：`5-7`、`1-3`、`2-7`、`1-8`、`4-7`、`1-6`。数一数会发现：**三条从顶点 1 出发、三条从顶点 7 出发**，而顶点 1 和顶点 7 正是立方体空间对角线的两个端点。所以画面看起来像两处汇聚的蜘蛛网。

于是"线框"这个词有两层含义：

- 你想要的："立体的棱边"；
- 代码画的："组成网格的每条三角形的边"。

纯四边形模型只有第一种；三角化之后两者就不同了。真实的建模软件会额外做**边去重**或者保留原始多边形信息，才能只显示棱边。

**M4 不需要这么做**，因为 M5 要把这些三角形填成实心面——到那时对角线会隐入面内，谁也不在意它。

## 第十一部分 · 测试：三类输入

解析器是程序与外部世界的接口，最值得测。而"测好文件能读"只覆盖了三分之一，还要测**坏数据**和**缺失文件**：

## 第十二部分 · 工具与语法（本次新增）

| 工具 / 语法 | 用途 |
| --- | --- |
| `git check-ignore -v 路径` | 查一个文件是被哪条规则挡住的；提交前查一次模型文件，能省一堆困惑 |
| `.gitignore` 里的 `!` | 反例规则，表示"这个路径不要忽略"，如 `!assets/*.obj` |
| `for (const T& x : 容器)` | 范围 for，遍历容器时优先用它，比手写下标更短且不容易越界 |
| `std::stoi(字符串)` | 字符串转整数 |
| `字符串.find('/')` 与 `std::string::npos` | 找子串位置；`npos` 表示"没找到" |
| `字符串.substr(起, 长)` | 取子串 |
| `std::ifstream` + `std::getline` + `std::istringstream` | 文件解析的三件套 |

**关于 `*.obj` 那个坑**：`.obj` 这个扩展名被两种完全不同的东西使用——微软编译器的**目标文件**，和三维模型的 **OBJ 格式**。很多 `.gitignore` 模板会忽略 `*.obj`，于是你的模型文件莫名其妙提交不上去。**遇到"文件明明在却提交不了"，第一件事就是跑 `git check-ignore`。**

## 第十三部分 · 自测题

1. 为什么模型文件用"顶点索引"而不是让每个三角形各写一遍坐标？
2. 一个立方体有 8 个顶点，为什么面表里有 12 行？
3. `f 5 6 7` 里的 5 对应 C++ 数组的哪个下标？
4. 面里出现 `f 1/2/3 4/5/6 7/8/9` 时，我们要哪一部分？怎么取？
5. 一个五边形的面，会被拆成几个三角形？为什么是这么多？
6. `transformPoint` 和 `transformVector` 有什么区别？什么时候必须用后者？
7. 绕 y 轴旋转 90°，`(1,0,0)` 会变成什么？（用右手定则推）
8. 为什么投影时要把 y 取反？
9. 正交投影和透视投影的区别是什么？
10. 归一化时为什么缩放倍数要取两个方向中较小的那个？
11. 求包围盒时初值为什么不能用 0？
12. 线框渲染出来的立方体上多出的对角线是怎么来的？

### 参考答案

1. 省空间（相邻三角形共享顶点），也省计算（每个顶点只需变换、计算一次，而不是每个三角形算三次）。
2. 立方体每个面是四边形，被拆成 2 个三角形，6 × 2 = 12。
3. `vertices[4]`——因为 OBJ 的索引从 1 开始，读入时要减 1。
4. 只要**顶点索引**，即第一个斜杠之前的部分；用 `find('/')` 找位置，再用 `substr(0, pos)` 截取。
5. 3 个。扇形拆分：以第 0 个顶点为中心，连成 (0,1,2)、(0,2,3)、(0,3,4)，共 n−2 个。
6. `transformPoint` 把输入当作位置，补齐次坐标并做 w 除法，**会受平移影响**；`transformVector` 把输入当作方向，不做这些，**不受平移影响**。变换法线时必须用后者。
7. `(0, 0, −1)`。右手拇指指向 +y，四指从 +x 转向 −z。
8. 模型空间 y 向上，画布 y 向下，两者方向相反。
9. 正交投影忽略 z，"远处和近处一样大"；透视投影用与 z 相关的 w 做除法，实现"近大远小"。
10. 取小的那个，两个方向就都能装下；同时两个方向共用同一个倍数，模型不会被拉变形。
11. 因为模型可能整体位于某个坐标的一侧（例如全部 x > 100），用 0 起手会把最小值污染成 0，导致尺寸和位置都错。
12. 四边形面在三角化时会产生一条被两个三角形共享的对角线，而线框会把每个三角形的三条边都画出来。

## 附录 · 术语表

| 中文 | 英文 | 含义 |
| --- | --- | --- |
| 顶点表 / 面表 | vertex / face list | 模型的两张核心数据表 |
| 索引数组 | index array | 用编号引用顶点，避免重复存储 |
| OBJ | Wavefront OBJ | 一种纯文本三维模型格式 |
| 三角形化 | triangulation | 把多边形拆成三角形 |
| 绕序 | winding | 面顶点的排列方向，决定正面朝向 |
| 正交投影 | orthographic projection | 忽略深度、不产生近大远小 |
| 透视投影 | perspective projection | 用 w 除法实现近大远小 |
| 归一化 | normalize | 把模型缩放到合适尺寸并居中 |
| 包围盒 | bounding box | 完全包住模型的最小轴对齐盒子 |
| 齐次坐标 | homogeneous coordinates | 补一个维度的表示法，让平移可写成矩阵乘法 |
| fixture | 测试夹具 | 专门为测试准备的数据文件 |
