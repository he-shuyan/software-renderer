## 第一部分 · 为什么全世界都在画三角形

四句话，每句都有实在的理由：

**三点必共面。** 三个不共线的点唯一确定一个平面。四个点就不一定了——用四边形当光栅化图元，会出现"这个四边形到底算哪个平面"的歧义。三角形没有这个问题。

**任何多边形都能拆成三角形。** 一个 n 边形可以三角化成 n−2 个三角形。所以只要有三角形光栅化，就有了一切。

**三个顶点正好够插值。** 面内任意一点都能写成三个顶点的线性组合，而且这个组合**唯一**（权重系数三个、约束两条：和为 1、点的两个坐标）。多一个顶点，解就不唯一了。

**硬件如此。** GPU 的光栅化单元只接受三角形。所有图形 API 画矩形、画圆、画曲面，最后都是先拆成三角形再送进硬件。

## 第二部分 · 判断"点在三角形内"的三条路线

**扫描线法。** 对每一行 y，求三条边与这条水平线的交点，把交点之间的像素填上。老派做法，对大多边形效率高，但要处理"顶点算一次还是两次""水平边怎么算"这类边界规则，很容易写错。

**重心坐标。** 算出 P 相对三个顶点的权重 `(w0, w1, w2)`，三个都非负就在内部。

**边界函数。** 判断 P 是否落在三条边的同一侧。

后两者其实是同一件事的两种说法：**边界函数值除以总面积就是重心坐标**。我们选它，因为代码最短、没有分支，而且顺手就把插值权重拿到了——GPU 里实际用的也是这个。

## 第三部分 · 边界函数

```cpp
double edge(const Vec2& a, const Vec2& b, const Vec2& p) {
    return (b.x - a.x) * (p.y - a.y) - (b.y - a.y) * (p.x - a.x);
}
```

**它是什么。** 二维叉积 `(b − a) × (p − a)`。二维叉积没有方向（只有一个分量），所以它就是个数。

**几何意义。** 叉积的绝对值等于两个向量张成的平行四边形面积；三角形是这个平行四边形的一半。所以：

```
edge(a, b, p) = 2 × 三角形 (a, b, p) 的有符号面积
```

**符号的意义。** `b − a` 是从 a 指向 b 的方向向量。如果 p 在这个方向的**右侧**，叉积为负；左侧为正（在标准数学坐标下）。这就是"同侧判定"的依据。

**在屏幕坐标里要注意。** 我们的 y 轴朝下，整个坐标系被镜像过，所以"哪边是正"和数学直觉相反。M3 里验证过：线段 `(0,0) → (10,0)`，点 `(5, 3)`（屏幕下方）得到 `+30`，点 `(5, -3)`（上方）得到 `−30`。

**手算演练（值得自己再算一遍）：**

```
a = (0,0)，b = (10,0)

p = (5, 3) :  (10−0)×(3−0) − (0−0)×(5−0) = 30     ← 正
p = (5, −3):  (10−0)×(−3−0) − (0−0)×(5−0) = −30   ← 负
p = (15, 0):  (10−0)×(0−0) − (0−0)×(15−0) = 0     ← 在延长线上
p = (5, 0) :  同样为 0                             ← 在线段上
```

**先在零件上验证，再组装。** 这一步的意义在于：如果一个"打印出四个数"的小测试能确认符号约定，那么后面整套判定就站在可靠的地基上。图形学代码里 90% 的 bug 是符号与方向错误，而它们都能用这种小测试提前拦下来。

## 第四部分 · 重心坐标

### 4.1 定义

对三角形 `(p0, p1, p2)` 和一点 P：

```
w0 = edge(p1, p2, P) / edge(p0, p1, p2)     ← 注意是"对面的那条边"
w1 = edge(p2, p0, P) / edge(p0, p1, p2)
w2 = edge(p0, p1, P) / edge(p0, p1, p2)
```

分母 `edge(p0, p1, p2)` 是整个三角形面积的两倍。

### 4.2 三个必须记住的性质

**第一，三者之和恒等于 1。** 几何上的解释最直观：点 P 把三角形切成三块小三角形——`(P, p1, p2)`、`(p0, P, p2)`、`(p0, p1, P)`——这三块的面积之和正好等于大三角形的面积。三个权重正是这三块面积占整体的比例，所以和为 1。

**第二，在每个顶点处有一个权重为 1、其余为 0。** P 落在 p0 上时，小三角形 `(P, p1, p2)` 就是大三角形本身（比例 1），另外两块面积为 0。

**第三，权重可以理解为"距离的对偶"。** 离 p0 越近，`w0` 越大；`w0` 正好在 p0 到对面那条边的连线上线性变化。

### 4.3 为什么插值是安全的

```
c = c0 · w0 + c1 · w1 + c2 · w2
```

这是一个**加权平均**：权重都在 `[0, 1]` 内，而且总和为 1。加权平均的结果必然落在最小值与最大值之间——所以颜色分量不可能超出 `[0, 255]`，**不需要钳制**。

对比一下：如果权重之和是 1.5，结果就可能到 1.5 倍亮度，需要额外写 `std::min`/`std::max` 去夹。重心坐标省掉了这个麻烦，这是它在图形学里无处不在的原因之一。

### 4.4 这套机制会一直用下去

`mix3` 现在混合的是颜色，但插值的对象可以换成任何顶点属性：

| 里程碑 | 插值的东西 | 用途 |
| --- | --- | --- |
| M5 | 深度值 z | 深度缓冲（谁在前谁在后） |
| M7 | 纹理坐标 u, v | 把贴图映射到面上 |
| M8 | 法线、光照强度 | 平滑的明暗过渡（Gouraud / Phong 着色） |

**M3 你写下的那个 `mix3`，是之后所有"平滑"的来源。**

## 第五部分 · 绕序与退化

### 5.1 为什么要统一绕序

顶点顺序决定了 `area2` 的正负：数学意义上逆时针为正、顺时针为负。再加上我们 y 轴朝下造成的镜像，"哪一个符号代表内部"会变得很绕。

**与其纠结符号，不如统一它**：

```cpp
if (area2 < 0.0) {
    std::swap(p1, p2);
    std::swap(c1, c2);
    area2 = -area2;
}
```

对调之后 `area2 > 0`，内部点的三个权重必然都 ≥ 0，判定只剩一个条件。

**关键是颜色也要跟着换。** 顶点和它的属性是一体的，换了位置不换颜色，就会出现"形状对但渐变方向反了"——这种 bug 看着很怪，但原因很朴素。

### 5.2 退化三角形

三个点共线时 `area2 == 0`，接下来 `edge(...) / area2` 就是**除以零**，结果是 NaN 或无穷大。NaN 之后 `lround` 的行为未定义，很可能直接崩溃。

所以那句提前返回不是可选的礼貌，而是必需的保护：

```cpp
if (area2 == 0.0) {
    return;
}
```

（浮点数用 `==` 比较通常不安全，但这里判断的是"面积是否恰好为零"这个精确情形，是少数可以接受的场景。）

## 第六部分 · 像素中心与包围盒

### 6.1 为什么用像素中心

像素 `(x, y)` 覆盖的其实是**从 `(x, y)` 到 `(x+1, y+1)` 那一个小方块**，它的中心在 `(x + 0.5, y + 0.5)`。

判定"这个像素属不属于三角形"，等价于问"这个格子的中心点是否被三角形覆盖"。这是最公平的规则：

- 如果改用左上角 `(x, y)`，整个三角形会往**左上**偏半个像素；
- 如果有两个三角形共享一条边，用中心判定能保证这条边上不会有缝隙、也不会有一条重复描边的像素带。

**边缘多一格或少一格，第一个要检查的就是这里。**

### 6.2 包围盒

三角形可能只覆盖画布的一小块。如果对 650 × 400 = 26 万个像素都做三次边界函数运算，成本是包围盒内像素数的几十倍。

包围盒就是"三角形最多能覆盖到的矩形"，用三个顶点的 min/max 算出来，再用 `floor` / `ceil` 转成整数范围。

**但必须夹到画布内**：

```cpp
const int minX = std::max(0, static_cast<int>(std::floor(minXd)));
const int maxX = std::min(image.width() - 1, static_cast<int>(std::ceil(maxXd)));
```

少了上界那一句，`setPixel` 就会往画布外写——段错误。M2 里旋转方框时已经遇到过同样的风险，画线函数里的边界检查也在做同一件事。**图形代码里凡是"算出来的坐标"，都必须假设它可能越界。**

## 第七部分 · 色相函数：把角度变成颜色

```cpp
static Color hueColor(double angle) {
    const double r = 0.5 + 0.5 * std::cos(angle);
    const double g = 0.5 + 0.5 * std::cos(angle - 2.0 * kPi / 3.0);
    const double b = 0.5 + 0.5 * std::cos(angle + 2.0 * kPi / 3.0);
    ...
}
```

`0.5 + 0.5 × cos(θ)` 把余弦从 `[−1, 1]` 平移到 `[0, 1]`，正好可以当颜色分量。三个余弦的相位**相差 120°**，也就是把圆周三等分，于是：

| θ | r | g | b | 观感 |
| --- | --- | --- | --- | --- |
| 0° | 1.00 | 0.25 | 0.25 | 红 |
| 120° | 0.25 | 1.00 | 0.25 | 绿 |
| 240° | 0.25 | 0.25 | 1.00 | 蓝 |

这实际上是 HSV 色相环的一个解析等价形式，好处是不用写那套分段函数。

**更值得记住的是背后的通用技巧：把方向的三个分量映射到 RGB。** 以后调试法线、切线、光照方向时，你会把 `(nx, ny, nz)` 直接当成 `(r, g, b)` 画出来——一张图就能看出方向上有没有错。这是图形学里最常用的可视化手法。

## 第八部分 · 用三角形逼近曲线

圆盘其实是用 12 个三角形拼的：

```cpp
const double a0 = 2.0 * kPi * i / slices;
const double a1 = 2.0 * kPi * (i + 1) / slices;

const Vec2 local0(0.0, 0.0);
const Vec2 local1(radius * std::cos(a0), radius * std::sin(a0));
const Vec2 local2(radius * std::cos(a1), radius * std::sin(a1));
```

**扇形不是图元。** "画圆"这件事在光栅化里根本不存在，只有"画足够多的小三角形，让它们看起来像圆"。

于是出现了一个典型的工程取舍：

- `slices` 小 → 顶点少、填充像素少、但边缘能看出棱角；
- `slices` 大 → 圆滑、但每个像素可能被多个三角形覆盖（**重复填充**），开销上升。

M3 里你选的 12 已经够用，而且**棱角本身就是信息**——它直观地告诉看代码的人"这是一个个三角形拼出来的"。

（顺带：如果两个相邻三角形共享一条边，而它们的颜色在共享顶点上不一致，就会出现一条可见的接缝。我们在色轮里让相邻扇形共用同一个 `hueColor(a)` 值，所以没有缝。）

## 第九部分 · 验证：面积不变量

```cpp
const double expected = 50000.0;   // 2 × 面积 = |400×300 − 100×200| = 100000
```

**理论值怎么算。** 三角形 `(100,50)`、`(500,150)`、`(300,350)`：

```
2 × 面积 = |(500−100)×(350−50) − (150−50)×(300−100)|
         = |400 × 300 − 100 × 200| = 100000
面积 = 50000
```

**实测 50100，比值 1.002。** 差的 100 个像素从哪来？三角形的周长大约是 1056 个像素，而 100 / 1056 ≈ 0.1 —— 也就是说，**平均每十个边界像素里才有一个"中心点正好压在边界上"**。它到底算命中还是没命中，取决于取整方向，这就是全部误差的来源。

**这里最值得记住的不是"通过"，而是"能解释误差从哪来"。**

- 如果比值是 0.7，那说明有大片区域没被填上；
- 如果是 1.3，说明有条件反了、填到了外面；
- 如果是 1.002，说明填充范围正确，误差只来自边界像素的离散化。

**能解释误差量级的人，才是在真正做测试。**

## 第十部分 · 命令与工具（本次新增）

| 命令 / 手法 | 用途 |
| --- | --- |
| `grep -n "drawTriangle" src/main.cpp` | 确认某个函数有没有被调用、在第几行——比翻文件快得多 |

## 第十一部分 · 自测题

1. 为什么图形学几乎只用三角形作为图元？（至少说三条理由）
2. `edge(a, b, p)` 的几何意义是什么？符号代表什么？
3. 在屏幕坐标里，线段 `(0,0)→(10,0)` 下方的点，`edge` 是正还是负？
4. 三个边界函数值同号，说明什么？
5. 重心坐标三个权重之和等于多少？为什么？
6. 为什么重心坐标插值不需要 clamp？
7. 为什么要"统一绕序"？交换顶点时为什么颜色也要一起换？
8. `area2 == 0` 时如果直接往下算，会发生什么？
9. 判定像素归属时为什么用 `(x+0.5, y+0.5)` 而不是 `(x, y)`？
10. 包围盒把范围夹到画布内，少了这一步会怎样？
11. 面积测试的比值是 1.002，这个偏差说明了什么？
12. 想让色轮边缘更圆滑，改哪个参数？代价是什么？

### 参考答案

1. 三点必共面；任何多边形都能三角化；三个顶点正好够唯一的线性插值；GPU 硬件只接受三角形。
2. 它是三角形 `(a, b, p)` 的有符号面积的两倍。符号表示 p 在直线 a→b 的哪一侧，绝对值表示三点围成的面积。
3. 正。屏幕坐标 y 向下，"下方"意味着 y 更大，代入得正值。
4. 该点在三角形内部（含边界）。
5. 等于 1。因为点 P 把三角形切成三块小三角形，它们的面积之和等于大三角形的面积，三个权重正是这三块所占的比例。
6. 因为三个权重非负且和为 1，插值是加权平均，结果必然落在三个顶点值之间。
7. 统一绕序后内部判定只需一个条件（`>= 0`），不必分情况讨论。颜色是顶点的属性，顶点换了位置而颜色不换，渐变方向就会反。
8. 会出现除以零，得到 NaN 或无穷大；`lround(NaN)` 行为未定义，很可能崩溃。
9. 因为像素实际覆盖的是从 `(x,y)` 到 `(x+1,y+1)` 的方格，中心才代表这个格子。用左上角会让整个三角形偏移半个像素，并让共享边出现缝隙或重复。
10. 会写出画布之外的内存 → 段错误。
11. 填充范围正确，误差只来自边界像素的取整（约每十个边界像素一个，与 0.1 像素的期望一致）。
12. 增大 `slices`。代价是更多三角形、更多顶点计算、以及同一像素被多个三角形重复填写的开销。

## 第十二部分 · 扩展练习

1. 把 `slices` 改成 36，再画一张，对比两张图的边缘。
2. 做一个"棋盘格"测试图：用两组不同朝向的三角形铺满画布，检查共享边上有没有缝隙或重复像素。
3. 给 `drawTriangle` 加一个"线框模式"（只画三条边），用来调试顶点位置。
4. 用 `hueColor` 给一个圆盘做**两层**：内圈用低饱和度、外圈用高饱和度，观察重心坐标插值在两圈交界处的表现。
5. 写一个把方向向量映射成 RGB 的小工具（`(x, y) → 颜色`），以后 M8 调试法线时会用到。
6. 让色轮转起来：写一个循环输出 12 帧（每帧 30°），文件名用 `frame_00.bmp` 这样的格式。这是走向动画的第一步。
